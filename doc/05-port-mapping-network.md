# 05. 포트와 네트워크

> 보고서 대응: [10번 포트 매핑](../README.md), 14-2 컨테이너 포트 원리, 15-2 포트 충돌

---

## 1. 포트란 무엇인가

IP 주소가 "건물 주소"라면 포트는 **"몇 호실"** 이다. 한 컴퓨터에서 여러 프로그램이 동시에 네트워크를 쓰므로, 들어온 데이터를 어느 프로그램에 줄지 구분해야 한다.

```
localhost:8081
└───┬───┘ └─┬─┘
  주소     포트 (0 ~ 65535)
```

| 범위 | 이름 | 특징 |
| :--- | :--- | :--- |
| 0 ~ 1023 | 잘 알려진 포트 | HTTP 80, HTTPS 443, SSH 22. 바인딩에 관리자 권한 필요 |
| 1024 ~ 49151 | 등록된 포트 | 8080, 3000, 5432 등 |
| 49152 ~ 65535 | 동적 포트 | OS가 임시로 할당 |

실습에서 80이 아니라 8081을 쓴 이유가 여기 있다. 80번은 관리자 권한이 필요하고 다른 서비스가 쓰고 있을 수 있다.

**핵심 규칙: 한 포트는 한 프로그램만 점유할 수 있다.** 보고서 15-2의 충돌이 이것 때문에 발생한다.

---

## 2. 컨테이너는 왜 격리되어 있나

컨테이너는 **네트워크 네임스페이스(network namespace)** 라는 리눅스 커널 기능으로 격리된다. 각 컨테이너는 자기만의 네트워크 스택을 가진다.

```
┌─────────────────── 호스트(macOS) ───────────────────┐
│                                                     │
│   localhost:8081  ← 호스트의 포트 공간               │
│         │                                           │
│         │  포트 매핑 (-p 8081:80)                   │
│         ▼                                           │
│   ┌─────────────────── 컨테이너 ──────────────┐     │
│   │  172.17.0.2                              │     │
│   │  :80  ← 컨테이너만의 독립된 포트 공간      │     │
│   └──────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────┘
```

각 컨테이너는 **자기만의 IP와 자기만의 포트 1~65535** 를 가진다. 그래서 컨테이너 3개가 전부 내부 80번을 써도 서로 충돌하지 않는다.

### 그래서 왜 직접 접속이 안 되나

호스트에서 `localhost:80` 을 치면 **호스트 자신의 80번**을 찾는다. 컨테이너의 80번이 아니다. 둘은 애초에 다른 네트워크 공간에 있다.

```
호스트의 localhost:80   ≠   컨테이너의 localhost:80
```

이 둘을 연결해 주는 게 포트 매핑이다.

## 3. 포트 매핑

```bash
docker run -d -p 8081:80 --name my-app my-web:v1
#               └─┬─┘ └┬┘
#                 │    └─ 컨테이너 포트 (안쪽)
#                 └────── 호스트 포트 (바깥쪽)
```

**순서를 외우는 법: 바깥에서 안으로.** 호스트가 먼저, 컨테이너가 나중이다.

```
사용자 → localhost:8081 → [Docker가 전달] → 컨테이너:80 → nginx
```

보고서 10번의 `docker ps` 출력이 이 관계를 보여준다.

```
PORTS
0.0.0.0:8081->80/tcp
└──┬───┘ └┬┘  └┬┘
   │      │    └─ 컨테이너 포트
   │      └────── 호스트 포트
   └───────────── 모든 인터페이스에서 수신
```

### 바인딩 주소

```bash
-p 8081:80              # 0.0.0.0:8081 — 외부 기기에서도 접속 가능
-p 127.0.0.1:8081:80    # 내 컴퓨터에서만 접속 가능
```

기본값 `0.0.0.0` 은 **같은 네트워크의 다른 기기도 접속할 수 있다**는 뜻이다. 개발 중 DB를 띄울 때는 `127.0.0.1` 로 묶는 게 안전하다.

### 여러 포트, 랜덤 포트

```bash
-p 8081:80 -p 8443:443     # 여러 개
-p 80                      # 호스트 포트를 랜덤 할당
-P                         # EXPOSE된 포트 전부 랜덤 할당
```

## 4. 포트 충돌 진단 — 보고서 15-2 사례

### 현상

```bash
docker run -d -p 8081:80 --name my-app2 my-web:v1
# 8553c743c5dc...
# docker: Error response from daemon: driver failed programming external
# connectivity on endpoint my-app2: Bind for 0.0.0.0:8081 failed:
# port is already allocated.
```

### 진단 순서

**① 에러 메시지부터 읽는다**

`Bind for 0.0.0.0:8081 failed` — 문제는 컨테이너 내부가 아니라 **호스트 포트 8081** 이다. 이 한 줄에 답이 다 있다.

**② 누가 점유 중인지 확인한다**

```bash
lsof -i :8081
# COMMAND     PID  USER   FD   TYPE  NODE NAME
# com.docke 90928 kim   171u  IPv6   TCP *:sunproxyadmin (LISTEN)
```

| 옵션 | 의미 |
| :--- | :--- |
| `lsof -i :8081` | 해당 포트를 쓰는 프로세스 (macOS/Linux) |
| `netstat -an \| grep 8081` | 포트 상태만 |

**③ Docker 컨테이너인지 확인한다**

```bash
docker ps
# 8081을 쓰는 컨테이너(my-app)를 특정
```

**④ 선택한다**

| 상황 | 조치 |
| :--- | :--- |
| 기존 컨테이너가 필요하다 | 새 컨테이너의 **호스트 포트**를 바꾼다 |
| 기존 컨테이너가 불필요하다 | `docker rm -f` 로 정리 |
| Docker 아닌 프로세스가 점유 | 그 프로그램을 종료하거나 포트를 피한다 |

### 해결

**컨테이너 포트는 그대로 두고 호스트 포트만 바꾼다.**

```bash
docker rm my-app2                                  # 실패한 컨테이너 먼저 정리
docker run -d -p 8082:80 --name my-app2 my-web:v1  # 호스트 포트만 8082로
```

결과:

```bash
docker ps --format "table {{.Names}}\t{{.Ports}}"
# NAMES     PORTS
# my-app2   0.0.0.0:8082->80/tcp
# my-app    0.0.0.0:8081->80/tcp
```

같은 이미지, 같은 내부 포트 80. **호스트 포트만 달라서 공존한다.** 이것이 포트 매핑을 분리해 둔 실질적 이득이다.

> **놓치기 쉬운 점**: `docker run` 이 실패해도 **컨테이너는 생성된다**(위 출력의 컨테이너 ID가 증거). 그래서 재시도 전에 `docker rm` 을 해야 "이름이 이미 사용 중"이라는 두 번째 에러를 피할 수 있다.

## 5. 컨테이너 간 통신 — 포트 매핑이 필요 없다

여기가 가장 중요한 개념이다. 보고서 17-2에서 실증했다.

### 실험

Compose에서 `client` 서비스는 **포트 매핑이 전혀 없는데도** `web` 에 접속했다.

```yaml
client:
  image: curlimages/curl:latest
  command: ["sh", "-c", "sleep 3; curl -s http://web:8080/"]
  #                                        └─ 서비스 이름 + 컨테이너 포트
```

```bash
docker compose logs client
# client-1  | <h1>hello, world!</h1>     ← 성공
```

### 증거 — 접속 출처 IP가 다르다

```bash
docker compose logs web
# web-1 | 172.18.0.3 - - [...] "GET / HTTP/1.1" 200 23 "-" "curl/8.21.0"
# web-1 | 172.18.0.1 - - [...] "GET / HTTP/1.1" 200 23 "-" "curl/8.7.1"
```

| IP | 정체 | 경로 |
| :--- | :--- | :--- |
| `172.18.0.3` | client 컨테이너 | 같은 네트워크에서 **직통** |
| `172.18.0.1` | 호스트 게이트웨이 | 호스트에서 **포트 매핑을 거쳐** |

### 결론

```
포트 매핑(-p)은 컨테이너끼리 통신할 때가 아니라
호스트 ↔ 컨테이너 경계를 넘을 때만 필요하다.
```

**실무적 의미**: DB 컨테이너는 포트를 호스트에 열지 않아도 된다. 앱 컨테이너가 같은 네트워크에서 서비스명으로 접속하면 된다. 포트를 안 열수록 공격 표면이 줄어든다.

```yaml
services:
  app:
    ports: ["8080:8080"]    # 사용자가 접속해야 하므로 열어야 함
  db:
    # ports 없음 — app 컨테이너만 db:5432 로 접속. 외부 노출 없음
```

## 6. Docker 네트워크 종류

```bash
docker network ls
# NETWORK ID     NAME                           DRIVER    SCOPE
# 3a67505907f1   workspace-decoration_default   bridge    local
```

| 종류 | 설명 | 용도 |
| :--- | :--- | :--- |
| `bridge` | 기본값. 가상 스위치로 컨테이너 연결 | 대부분의 경우 |
| `host` | 호스트 네트워크를 그대로 사용 | 성능이 극도로 중요할 때 (Linux 전용) |
| `none` | 네트워크 없음 | 완전 격리가 필요할 때 |

### 기본 bridge vs 사용자 정의 bridge

**중요한 차이가 있다.**

| 항목 | 기본 bridge | 사용자 정의 bridge (Compose가 만드는 것) |
| :--- | :--- | :--- |
| 서비스명 DNS 해석 | ❌ 안 됨 | ✅ 됨 |
| 컨테이너 간 통신 | IP로만 | 이름으로 |

```bash
# 기본 bridge — 이름으로 못 찾는다
docker run -d --name web nginx
docker run --rm curlimages/curl curl http://web/
# curl: (6) Could not resolve host: web

# 사용자 정의 네트워크 — 이름으로 찾는다
docker network create mynet
docker run -d --name web --network mynet nginx
docker run --rm --network mynet curlimages/curl curl -s http://web/
# <html>...
```

Compose는 자동으로 프로젝트 전용 네트워크를 만들기 때문에 서비스명 접속이 바로 된다. 이것이 보고서 17-2에서 `http://web:8080` 이 동작한 이유다.

## 7. 서비스 디스커버리

컨테이너 IP는 재시작할 때마다 바뀐다. 그래서 IP를 하드코딩하면 곧 깨진다.

```
❌ http://172.18.0.3:8080     ← 재시작하면 IP가 바뀜
✅ http://web:8080            ← 서비스명은 안정적
```

Docker는 사용자 정의 네트워크에 **내장 DNS 서버(127.0.0.11)** 를 붙인다. 컨테이너가 `web` 을 조회하면 현재 IP를 알려준다.

```bash
docker compose exec client nslookup web
# Server:    127.0.0.11        ← Docker 내장 DNS
# Address:   172.18.0.2        ← web 의 현재 IP
```

## 8. 접속 검증에 쓴 명령의 옵션

포트 매핑이 동작하는지 확인할 때 쓴 두 명령이다.

### `curl -s` 와 `curl -I`

보고서 10번은 두 가지를 확인했다. **헤더로 응답 상태를, 본문으로 내용을** 본다.

```bash
curl -sI localhost:8081     # HTTP/1.1 200 OK ...
curl -s  localhost:8081     # <h1>hello, world!</h1>
```

| 옵션 | 이름 | 역할 |
| :--- | :--- | :--- |
| `-s` | silent | 진행률 표시기와 **에러 메시지**를 숨김 |
| `-I` | head | **헤더만** 받는다 (HEAD 요청) |
| `-i` | include | 헤더 + 본문 |
| `-S` | show-error | `-s` 중에도 에러는 표시 (`-sS` 로 조합) |
| `-v` | verbose | 요청·응답 과정 전체 |
| `-o` | output | 파일로 저장 |
| `-L` | location | 리다이렉트 따라가기 |

#### `-s` 는 에러도 숨긴다

`-s` 를 붙이지 않으면 진행률 표시기가 앞에 붙어 로그가 지저분해진다. 그래서 문서에 붙일 출력에는 `-s` 를 쓴다. 다만 **숨기는 대상이 진행률만이 아니다.**

```bash
curl localhost:9999
# curl: (7) Failed to connect to localhost port 9999 ...
# 종료코드 7

curl -s localhost:9999
# (아무것도 출력되지 않는다)
# 종료코드 7
```

진행률과 에러 메시지가 **둘 다 stderr로 나가기 때문에** `-s` 가 함께 막는다. 스크립트에서 `-s` 만 믿으면 실패를 놓치므로, **판단은 종료 코드로 한다.** 위에서 보듯 실패해도 `7` 은 정확히 돌아온다. 에러는 보고 싶다면 `-sS` 를 쓴다.

#### `-I` 는 본문을 받지 않는다

`-I` 는 단순히 헤더만 골라 보여주는 게 아니라 **HTTP 메서드 자체를 `HEAD` 로 바꾼다.** 서버는 헤더만 보내고 본문은 아예 전송하지 않는다.

```bash
curl -sI localhost:8081 | wc -c    # 236
curl -si localhost:8081 | wc -c    # 259
```

차이가 정확히 **23바이트**인데, 이는 `index.html` 의 크기이자 응답 헤더의 `Content-Length: 23` 과 일치한다. `-i` 는 본문까지 받았고 `-I` 는 받지 않았다는 뜻이다.

그래서 큰 파일이 있는 서버의 생존 여부만 확인할 때 `-I` 가 적합하다. 응답 상태는 알 수 있으면서 대역폭을 쓰지 않는다.

#### 주소에서 생략된 것

```
localhost:8081  →  실제 요청은  http://localhost:8081/
```

프로토콜은 `http://`, 경로는 `/` 가 기본값이다. `-v` 로 확인할 수 있다.

```bash
curl -sv localhost:8081
# > GET / HTTP/1.1          ← 경로가 / 로, 메서드가 GET 으로 채워졌다
# > Host: localhost:8081
```

**여기서 `8081` 은 호스트 포트다.** 컨테이너 내부 포트(80 또는 8080)로는 접속할 수 없다. 두 `localhost` 가 서로 다른 네트워크 네임스페이스에 있기 때문이다 (2장 참고).

### `docker ps --filter` 와 `--format`

보고서 8·11·15-2번이 목록을 좁히고 다듬을 때 쓴 옵션이다.

```bash
docker ps -a --filter name=my-app
# CONTAINER ID   IMAGE       ...   NAMES
# 4f5751723918   my-web:v1   ...   my-app
```

`--filter`(=`-f`)는 조건에 맞는 것만 남긴다. **여러 번 주면 AND로 결합된다.**

```bash
docker ps -a --filter status=exited --filter ancestor=hello-world
# 종료된 것 중에서 hello-world 이미지로 만든 것만
```

| 자주 쓰는 필터 | 뜻 |
| :--- | :--- |
| `name=문자열` | 이름에 그 문자열이 **포함**된 것 (완전 일치가 아니다) |
| `status=exited` | 상태 (`running`, `exited`, `created`, `paused`) |
| `ancestor=이미지` | 그 이미지로 만든 컨테이너 |
| `label=키=값` | 라벨 |

`--format` 은 **출력 열을 직접 고른다.** Go 템플릿 문법을 쓴다.

```bash
docker ps -a --format "table {{.Names}}\t{{.Status}}"
# NAMES     STATUS
# my-app    Up 10 minutes
```

| 조각 | 역할 |
| :--- | :--- |
| `table` | 머리글 줄을 붙인다 (없으면 데이터만) |
| `{{.Names}}` | 열 이름. `.Image`, `.Status`, `.Ports`, `.ID` 등 |
| `\t` | 열 구분 |

`docker ps -a` 를 그냥 실행하면 한 줄이 **119자**라 문서에 붙이면 가로로 넘친다. `--format` 으로 필요한 열만 남기면 30자 안팎으로 줄어든다. 보고서가 이 옵션을 쓴 이유다.

같은 문법이 다른 명령에도 통한다.

```bash
docker images my-web --format "{{.Repository}}:{{.Tag}} {{.CreatedSince}}"
docker version --format '{{.Server.Version}}'
docker info --format '{{.KernelVersion}}'
```

특히 `docker version --format '{{.Server.Version}}'` 은 **데몬이 죽어 있으면 종료 코드 1로 실패**하므로, 스크립트에서 데몬 생존 확인에 쓰기 좋다.

## 9. 직접 해보기

```bash
cd ~/Desktop && mkdir net-practice && cd net-practice
echo '<h1>net test</h1>' > index.html

cat > Dockerfile <<'EOF'
FROM nginx:latest
COPY index.html /usr/share/nginx/html/index.html
EOF

docker build -t nettest:v1 .

# 1. 포트 매핑 없이 실행 — 호스트에서 접속 불가
docker run -d --name no-port nettest:v1
curl --max-time 3 localhost:8888 || echo "→ 접속 불가 (당연함)"

# 2. 포트 매핑하고 실행
docker run -d -p 8888:80 --name with-port nettest:v1
curl -s localhost:8888
# <h1>net test</h1>

# 3. 포트 충돌 재현
docker run -d -p 8888:80 --name conflict nettest:v1
# port is already allocated 에러

# 4. 점유자 확인
lsof -i :8888
docker ps --format "table {{.Names}}\t{{.Ports}}"

# 5. 호스트 포트만 바꿔 해결
docker rm conflict
docker run -d -p 8889:80 --name conflict nettest:v1
curl -s localhost:8889

# 6. 컨테이너 간 통신 — 포트 매핑 없는 no-port 에도 접속된다
docker network create testnet
docker run -d --name inner --network testnet nettest:v1
docker run --rm --network testnet curlimages/curl curl -s http://inner/
# <h1>net test</h1>          ← 포트 매핑 없이 성공

# 7. 정리
docker rm -f no-port with-port conflict inner
docker network rm testnet
docker rmi nettest:v1
cd ~/Desktop && rm -r net-practice
```

**확인 문제**

1. `-p 8081:80` 에서 앞뒤 숫자는 각각 무엇인가?
2. 컨테이너 3개가 전부 내부 80번을 써도 괜찮은 이유는?
3. DB 컨테이너에 `ports:` 를 안 쓰면 앱이 접속할 수 있나?

<details>
<summary>답</summary>

1. 앞이 호스트 포트, 뒤가 컨테이너 포트. "바깥에서 안으로" 순서다.
2. 각 컨테이너가 독립된 네트워크 네임스페이스를 가져 자기만의 포트 공간을 쓰기 때문. 충돌은 호스트 포트에서만 발생한다.
3. 접속할 수 있다. 같은 네트워크 안이면 서비스명과 컨테이너 포트로 직접 통신한다. `ports:` 는 호스트에서 들어올 때만 필요하다.
</details>

## 10. 자주 하는 실수

| 실수 | 증상 | 해결 |
| :--- | :--- | :--- |
| `-p` 순서를 거꾸로 (`-p 80:8081`) | 접속 안 됨 | 호스트:컨테이너 순서 |
| 포트 충돌 시 컨테이너 포트를 바꿈 | 여전히 실패 | 호스트 포트만 바꾸면 된다 |
| 실패한 컨테이너를 안 지우고 재시도 | 이름 충돌 | `docker rm` 후 재시도 |
| 컨테이너 간 통신에 `localhost` 사용 | 연결 실패 | 서비스명 사용 (`http://web`) |
| 컨테이너 간 통신에 호스트 포트 사용 | 연결 실패 | 컨테이너 포트 사용 |

### A. 루브릭 직결 문항

#### A-1. 컨테이너 내부 포트로 직접 접속할 수 없는 이유와, 포트 매핑이 필요한 이유는?

**⚡ 30초 답변**

> 컨테이너는 **독립된 네트워크 네임스페이스**를 갖습니다. 자기만의 IP와 자기만의 포트 1~65535를 따로 가진다는 뜻입니다. 그래서 호스트에서 `localhost:80` 을 치면 호스트 자신의 80번을 찾지, 컨테이너의 80번을 찾지 않습니다. 두 `localhost` 는 애초에 다른 공간입니다.
>
> 포트 매핑은 그 둘을 잇는 통로를 뚫는 것이고, 필요한 이유는 세 가지입니다. **격리 유지** — 모든 포트를 자동 공개하면 격리의 의미가 없으니 공개할 포트만 고르게 합니다. **포트 충돌 회피** — 컨테이너가 전부 내부 80번을 써도 호스트 포트만 다르면 공존합니다. **이식성** — 내부 포트는 이미지에 고정하고 호스트 포트만 환경에 맞춰 바꿀 수 있습니다.

**보충 — "그럼 어떻게 전달되나?"를 물으면**

> 호스트 포트로 들어온 패킷을 컨테이너 IP와 포트로 **주소를 바꿔서 전달**합니다. Linux에서는 커널의 NAT 규칙이 이 일을 하고, macOS는 Docker Desktop이 리눅스 VM을 돌리므로 VM을 한 번 더 거칩니다. 실습 환경이 macOS인데 `docker version` 에서 Client가 `darwin/arm64`, Server가 `linux/arm64` 로 갈리는 게 그 구조를 보여줍니다.

**📄 근거**: 보고서 **14-2** + **10번**(`0.0.0.0:8081->80/tcp`)

**주의 — 이렇게 답하면 감점**
- ❌ "보안 때문에 막혀 있습니다" → 막아 놓은 게 아니라 **애초에 다른 네트워크 공간**이다. 차단이 아니라 분리다.
- ❌ "포트를 열어주는 것입니다" → `-p` 는 방화벽을 여는 게 아니라 **주소를 변환해 전달**하는 것이다.

---

#### A-2. "호스트 포트가 이미 사용 중"이라 포트 매핑이 실패한다면, 어떤 순서로 진단하나?

**⚡ 30초 답변 — 5단계로 말한다**

> **1단계, 에러 메시지를 끝까지 읽습니다.**
>
> ```
> Bind for 0.0.0.0:8081 failed: port is already allocated.
> ```
>
> 여기서 두 가지가 확정됩니다. 문제는 컨테이너 내부가 아니라 **호스트 포트 8081**이고, 원인은 권한이나 설정이 아니라 **이미 점유됨**입니다.
>
> **2단계, 점유자를 찾습니다.** `lsof -i :8081`
>
> **3단계, 그게 Docker인지 확인합니다.** `docker ps` 로 8081을 쓰는 컨테이너를 특정합니다. Docker가 아닌 다른 프로그램일 수도 있어서 이 구분이 필요합니다.
>
> **4단계, 선택합니다.** 기존 컨테이너가 필요하면 새 컨테이너의 **호스트 포트만** 바꾸고, 필요 없으면 정리합니다.
>
> **5단계, `curl` 로 재검증합니다.**

**핵심 포인트 — 이 한 문장을 꼭 넣는다**

> 고칠 대상은 이미지도, 컨테이너 포트도 아닌 **호스트 포트 하나**입니다. 컨테이너 내부는 80번 그대로 두고 `-p 8082:80` 으로 바꿔서 두 컨테이너를 공존시켰습니다.

**가산점 — 실제로 겪어야 아는 것**

> 한 가지 더 있는데, **`docker run` 이 실패해도 컨테이너는 생성됩니다.** 에러 메시지 위에 컨테이너 ID가 찍히는 게 그 증거입니다. 그래서 재시도 전에 `docker rm` 을 하지 않으면 "이름이 이미 사용 중"이라는 두 번째 에러를 만납니다.

**📄 근거**: 보고서 **15-2** (실제 재현 → 진단 → 해결 → 검증)

---

#### A-3. 컨테이너끼리 통신할 때도 포트 매핑이 필요한가?

**⚡ 30초 답변**

> 필요 없습니다. 같은 사용자 정의 네트워크에 있으면 **서비스명과 컨테이너 포트**로 직접 통신합니다. 실습에서 `client` 서비스는 `ports:` 가 전혀 없는데도 `http://web:8080` 으로 접속에 성공했습니다.

**결정적 증거 — 로그의 출처 IP**

```
172.18.0.3 - - [...] "GET / HTTP/1.1" 200 23 "-" "curl/8.21.0"   ← client 컨테이너 (직통)
172.18.0.1 - - [...] "GET / HTTP/1.1" 200 23 "-" "curl/8.7.1"    ← 호스트 (게이트웨이 경유)
```

> 같은 페이지에 대한 요청인데 출처가 갈립니다. 컨테이너끼리는 `172.18.0.x` 대역에서 직접 오가고, 호스트에서 온 요청만 게이트웨이(`172.18.0.1`)를 통과합니다. 즉 **포트 매핑은 호스트 경계를 넘을 때만 필요**합니다.

**실무로 연결 — 이걸 말하면 이해도가 드러난다**

> 그래서 DB 컨테이너는 `ports:` 를 안 쓰는 게 맞습니다. 앱 컨테이너가 같은 네트워크에서 `db:5432` 로 접속하면 되고, 호스트에 포트를 열지 않으면 외부에서 DB에 닿을 방법 자체가 없어집니다. 포트를 안 열수록 공격 표면이 줄어듭니다.

**📄 근거**: 보고서 **17-2** + **8번**(nginx 액세스 로그)

### B. 따라붙기 쉬운 후속 질문

#### B-1. `-p 8081:80` 에서 앞뒤 숫자는 각각 무엇인가?

> 앞이 호스트 포트, 뒤가 컨테이너 포트입니다. **"바깥에서 안으로"** 순서로 외웁니다. 사용자가 `localhost:8081` 로 들어오면 컨테이너의 80번으로 전달됩니다.

거꾸로 쓰면(`-p 80:8081`) 호스트 80번으로 들어온 요청이 컨테이너 8081번을 찾는데, nginx는 80번에서 듣고 있으니 연결이 안 된다.

---

#### B-2. `EXPOSE` 를 쓰면 포트가 열리나?

> 아닙니다. `EXPOSE` 는 **문서화 지시자**로, "이 이미지는 이 포트를 쓴다"는 메타데이터일 뿐입니다. 실제 공개는 `docker run -p` 나 Compose의 `ports:` 가 합니다.
>
> 다만 쓸모가 아예 없진 않습니다. `docker run -P`(대문자)를 쓰면 `EXPOSE` 된 포트들을 호스트의 임의 포트에 자동으로 매핑해 줍니다.

---

#### B-3. 컨테이너 3개가 전부 내부 80번을 써도 괜찮은 이유는?

> 각 컨테이너가 독립된 네트워크 네임스페이스를 가져서 **자기만의 포트 공간**을 쓰기 때문입니다. 충돌은 호스트 포트에서만 발생합니다. 실습에서 `my-app` 과 `my-app2` 가 둘 다 내부 80번인데 호스트 포트만 8081, 8082로 달라서 공존했습니다.

---

#### B-4. 왜 80번이 아니라 8081번을 썼나?

> 두 가지 이유입니다. 첫째, **1024번 미만은 잘 알려진 포트**라 바인딩에 관리자 권한이 필요합니다. 둘째, 80번은 다른 서비스가 이미 쓰고 있을 가능성이 높습니다. 개발 환경에서는 8080, 8081 같은 상위 포트를 쓰는 게 관례입니다.

---

#### B-5. 컨테이너 간 통신에 `localhost` 를 쓰면 왜 안 되나?

> 컨테이너 안에서 `localhost` 는 **그 컨테이너 자신**을 가리킵니다. `client` 안에서 `localhost:8080` 을 치면 client 자신의 8080번을 찾는데 거기엔 아무것도 없습니다. 상대 컨테이너를 가리키려면 서비스명(`web`)을 써야 합니다.
>
> 같은 이유로 **호스트 포트를 쓰는 것도 틀립니다.** `http://web:8081` 이 아니라 `http://web:8080` 입니다. 컨테이너 간에는 호스트 매핑을 거치지 않고 컨테이너 포트로 직접 가기 때문입니다.

| 잘못된 예 | 왜 틀렸나 | 올바른 예 |
| :--- | :--- | :--- |
| `http://localhost:8080` | 자기 자신을 가리킴 | `http://web:8080` |
| `http://web:8081` | 8081은 호스트 포트 | `http://web:8080` |
| `http://172.18.0.3:8080` | 재시작하면 IP가 바뀜 | `http://web:8080` |

---

#### B-6. 서비스 이름이 어떻게 IP로 바뀌나?

> Docker가 사용자 정의 네트워크에 **내장 DNS 서버**를 붙여 줍니다. 컨테이너의 `/etc/resolv.conf` 가 이 DNS(`127.0.0.11`)를 가리키고, 여기에 서비스명이 등록되어 있어 현재 IP를 알려줍니다.
>
> 컨테이너 IP는 재시작할 때마다 바뀌기 때문에 IP를 하드코딩하면 곧 깨집니다. 서비스명은 안정적이라 이걸 씁니다.

---

#### B-7. 그냥 `docker run` 으로 띄운 컨테이너끼리는 이름으로 통신되나?

> 안 됩니다. **기본 bridge 네트워크는 이름 해석을 지원하지 않습니다.** `Could not resolve host: web` 이 납니다.
>
> Compose가 서비스명 접속이 되는 이유는 프로젝트마다 **사용자 정의 네트워크**를 자동으로 만들기 때문입니다. `docker run` 으로 같은 걸 하려면 `docker network create` 로 네트워크를 만들고 `--network` 로 붙여야 합니다.

| | 기본 bridge | 사용자 정의 bridge |
| :--- | :--- | :--- |
| 서비스명 DNS 해석 | ❌ | ✅ |
| 만들어지는 시점 | Docker 설치 시 자동 | `network create` 또는 Compose |

---

#### B-8. `0.0.0.0:8081->80/tcp` 에서 `0.0.0.0` 은?

> **모든 네트워크 인터페이스에서 수신**한다는 뜻입니다. 같은 와이파이에 있는 다른 기기도 제 IP로 접속할 수 있습니다.
>
> 내 컴퓨터에서만 접근하게 하려면 `-p 127.0.0.1:8081:80` 으로 묶습니다. 개발 중 DB를 띄울 때는 이렇게 하는 게 안전합니다.

---

### C. 실전 진단 시나리오

#### C-1. "접속이 안 됩니다." 어디부터 보나?

> **안에서 밖으로 순서대로 좁힙니다.**
>
> ```bash
> docker ps                              # ① 컨테이너가 떠 있나
> docker logs <이름>                     # ② 앱이 정상 기동했나
> docker exec <이름> curl localhost:80   # ③ 컨테이너 안에서는 되나
> docker port <이름>                     # ④ 포트 매핑이 걸려 있나
> curl localhost:8081                    # ⑤ 호스트에서 되나
> ```
>
> **③에서 되는데 ⑤에서 안 되면 포트 매핑 문제**이고, **③에서도 안 되면 애플리케이션 문제**입니다. 이 한 번의 분기로 범위가 절반으로 줄어듭니다.

---

#### C-2. 컨테이너는 떠 있는데 `curl` 이 연결을 거부한다면?

> 세 가지를 순서대로 봅니다.
>
> 1. **포트 매핑 자체가 없는가** — `docker ps` 의 PORTS 열이 비어 있으면 `-p` 를 안 준 것입니다.
> 2. **매핑은 있는데 컨테이너 포트가 틀린가** — 앱이 8080에서 듣는데 `-p 8081:80` 으로 매핑했다면 80번엔 아무도 없습니다. `docker exec` 로 안에서 확인합니다.
> 3. **앱이 `127.0.0.1` 에만 바인딩했는가** — 컨테이너 안에서 앱이 루프백에만 붙어 있으면 외부에서 못 들어옵니다. `0.0.0.0` 으로 바인딩해야 합니다. 실습의 nginx 설정에서 `listen 8080;` 이 특정 IP 없이 쓰인 게 이 경우입니다.

3번은 특히 놓치기 쉽다. 컨테이너 안에서는 잘 되는데 밖에서만 안 되는 전형적인 원인이다.

---

#### C-3. 포트를 정리하고 싶다. 무엇부터 확인하나?

```bash
docker ps --format "table {{.Names}}\t{{.Ports}}"   # 어떤 컨테이너가 어느 포트를
lsof -i :8081                                        # Docker 밖의 프로세스까지
docker compose down                                  # Compose로 띄웠다면
```

> Docker가 아닌 프로그램이 점유한 경우도 있으므로 `docker ps` 만 보고 판단하면 안 됩니다. `lsof` 로 한 번 더 확인합니다.

| 왜 직접 접속 못 하나 | 컨테이너가 독립된 네트워크 네임스페이스를 가져서 |
| `-p` 순서 | 바깥에서 안으로 (호스트:컨테이너) |
| `EXPOSE` | 문서화일 뿐, 실제 공개는 `-p` |
| 포트 충돌 | 고칠 건 **호스트 포트** 하나 |
| 컨테이너 간 통신 | 서비스명 + **컨테이너 포트**, 매핑 불필요 |
| 진단 순서 | 안(`exec`) → 밖(`curl`) 으로 좁히기 |
