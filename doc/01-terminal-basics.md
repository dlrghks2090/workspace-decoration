## 1. 셸이 하는 일

터미널에 문자를 치면 **셸(shell)** 이라는 프로그램이 그것을 읽어 해석하고, 실제 프로그램을 실행한 뒤 결과를 돌려준다. macOS의 기본 셸은 `zsh` 다.

```bash
echo $SHELL
# /bin/zsh
```

명령을 입력하면 셸은 이렇게 처리한다.

```
사용자 입력:  cp memo.txt backup.txt
           └┬┘└───┬───┘└────┬───┘
           명령어  인자1     인자2

1. 공백을 기준으로 쪼갠다 (토큰화)
2. 첫 단어(cp)를 PATH에서 찾는다 → /bin/cp
3. 나머지를 인자로 넘겨 실행한다
4. 종료 코드를 받는다 (0 = 성공)
```

**종료 코드**는 자동화에서 중요하다. 직전 명령의 성공 여부를 알려준다.

```bash
ls /존재하지않는경로
echo $?
# 1   ← 0이 아니면 실패
```

## 2. 경로 — 가장 먼저 이해할 개념

### 절대 경로와 상대 경로

| 구분 | 시작 | 예시 | 특징 |
| :--- | :--- | :--- | :--- |
| **절대 경로** | `/` (루트) | `/Users/kim/Desktop/memo.txt` | 어디서 실행해도 같은 곳을 가리킨다 |
| **상대 경로** | 현재 위치 | `Desktop/memo.txt` | 현재 위치가 바뀌면 다른 곳을 가리킨다 |

### 특수 기호

| 기호 | 의미 | 예시 |
| :--- | :--- | :--- |
| `.` | 현재 디렉토리 | `docker build .` ← 현재 폴더를 빌드 컨텍스트로 |
| `..` | 상위 디렉토리 | `cd ..` |
| `~` | 홈 디렉토리 | `~/.ssh/id_ed25519` = `/Users/kim/.ssh/id_ed25519` |
| `-` | 직전 디렉토리 | `cd -` ← 왔던 곳으로 되돌아감 |

```bash
pwd
# /Users/kim/Desktop/kan

cd ..           # 상위로
pwd
# /Users/kim/Desktop

cd -            # 직전 위치로 되돌아감
pwd
# /Users/kim/Desktop/kan
```

### 언제 무엇을 쓰는가

보고서 14-3에서 다루는 판단 기준이다.

```
실행 위치가 달라져도 같은 대상을 가리켜야 한다  →  절대 경로
프로젝트를 통째로 옮겨도 따라와야 한다          →  상대 경로
```

**예시로 이해하기**

```dockerfile
# Dockerfile 안 — 상대 경로가 맞다
COPY index.html /usr/share/nginx/html/index.html
#    └─── 상대: 빌드 컨텍스트 기준. 저장소를 어디에 클론해도 동작
#                              └─── 절대: 컨테이너 내부 경로는 항상 절대
```

만약 `COPY /Users/kim/project/index.html ...` 이라고 절대 경로로 썼다면, 다른 사람이 클론했을 때 그 경로가 없어서 빌드가 실패한다.

반대로 cron(스케줄러)이 실행하는 스크립트에서 상대 경로를 쓰면, 실행 시점의 작업 디렉토리를 예측할 수 없어 파일을 못 찾는다. 이때는 절대 경로가 맞다.

## 3. 위치 확인과 이동

### pwd — 현재 위치 출력

```bash
pwd
# /Users/kim/Desktop
```

`print working directory`의 약자다. 길을 잃었을 때 가장 먼저 치는 명령이다.

### ls — 목록 보기

```bash
ls              # 이름만
ls -l           # 상세 정보 (권한, 소유자, 크기, 시각)
ls -a           # 숨김 파일 포함 (.으로 시작하는 파일)
ls -la          # 둘 다
ls -lh          # 크기를 사람이 읽기 좋게 (1.2K, 3.4M)
ls -d kan       # 디렉토리 자체 정보 (내용물이 아니라)
```

**`-d` 가 중요한 이유**

```bash
ls workspace
# (workspace 안의 파일 목록이 나옴)

ls -d workspace
# workspace          ← 디렉토리 자체
```

권한을 확인할 때 `ls -l workspace` 를 치면 안의 파일들 권한이 나온다. 디렉토리 자신의 권한을 보려면 `ls -ld workspace` 를 써야 한다. 보고서 6번에서 이 차이를 썼다.

### cd — 이동

```bash
cd kan              # 하위 폴더로
cd ..               # 상위로
cd ~                # 홈으로 (그냥 cd 만 쳐도 같음)
cd /usr/local/bin   # 절대 경로로
cd -                # 직전 위치로
```

## 4. 디렉토리 만들기와 지우기

### mkdir

```bash
mkdir kan                    # 폴더 하나
mkdir -p a/b/c               # 중간 경로까지 한 번에 (parents)
```

`-p` 없이 `mkdir a/b/c` 를 치면 `a` 가 없을 때 실패한다. `-p` 는 없는 중간 단계를 알아서 만들어 준다. 이미 있어도 에러를 내지 않아서 스크립트에서 자주 쓴다.

### rmdir / rm -r

```bash
rmdir empty-folder        # 빈 디렉토리만 삭제 가능
rm -r kan                 # 내용물까지 통째로 (recursive)
```

**왜 `rm` 만으로는 디렉토리가 안 지워지는가?**

```bash
rm kan
# rm: kan: is a directory
```

안전장치다. 디렉토리 안에 무엇이 들었는지 모른 채 지우는 사고를 막으려고, "안의 것까지 지우겠다"는 의사를 `-r` 로 명시하게 한다.

## 5. 파일 만들기와 보기

### 만들기

```bash
touch memo.txt                      # 빈 파일 생성 (이미 있으면 수정시각만 갱신)
echo "Terminal Practice" > memo.txt # 내용을 넣으며 생성 (덮어쓰기)
echo "두 번째 줄" >> memo.txt        # 이어 붙이기 (append)
```

`>` 와 `>>` 의 차이는 사고 방지에 중요하다.

| 기호 | 동작 | 위험 |
| :--- | :--- | :--- |
| `>` | 기존 내용을 **지우고** 새로 씀 | 실수하면 원본 소실 |
| `>>` | 기존 내용 **뒤에 추가** | 안전 |

### 보기

```bash
cat memo.txt          # 전체 출력
head -5 memo.txt      # 앞 5줄
tail -5 memo.txt      # 뒤 5줄
tail -f app.log       # 실시간으로 따라가며 출력 (로그 볼 때)
less memo.txt         # 페이지 단위로 (q 로 종료)
wc -l memo.txt        # 줄 수 세기
```

파일이 크면 `cat` 은 화면을 순식간에 지나가므로 `less` 나 `head`/`tail` 을 쓴다.

## 6. 복사 · 이동 · 삭제

### cp — 복사

```bash
cp memo.txt backup.txt            # 파일 복사
cp -r archive archive-backup      # 디렉토리 복사 (-r 필요)
cp memo.txt ~/Desktop/            # 다른 위치로
```

### mv — 이동과 이름 변경

**`mv` 는 하나의 명령이 두 가지 일을 한다.** 보고서 5번에서 네 가지 경우를 모두 기록했다.

```bash
# 1. 파일 이름 변경 (같은 디렉토리 안)
mv memo.txt notes.txt

# 2. 파일 이동 (다른 디렉토리로)
mv notes.txt archive/

# 3. 디렉토리 이름 변경
mv archive archive-old

# 4. 디렉토리 이동
mv archive-old ~/Desktop/
```

**왜 같은 명령인가?** 파일시스템 입장에서 "이름 변경"과 "이동"은 같은 작업이기 때문이다. 둘 다 *경로(이름)를 다른 경로로 바꾸는 것*이다. 데이터 자체는 그대로 있고 이름표만 바뀐다. 그래서 같은 디스크 안에서의 `mv` 는 파일이 아무리 커도 즉시 끝난다.

```
mv memo.txt notes.txt
   └─ 데이터는 디스크에 그대로, "memo.txt"라는 이름만 "notes.txt"로 교체
```

반면 다른 디스크로 옮기면 실제 복사 후 삭제가 일어나므로 시간이 걸린다.

### rm — 삭제

```bash
rm memo.txt          # 파일 삭제
rm -r archive        # 디렉토리 삭제
rm -i memo.txt       # 삭제 전 확인 (interactive)
rm -f memo.txt       # 확인 없이 강제 (force)
```

> **주의**: 터미널의 `rm` 은 휴지통으로 보내지 않는다. **즉시 완전 삭제**다. 특히 `rm -rf` 는 확인 없이 통째로 지우므로, 실행 전 경로를 반드시 두 번 확인한다.

안전 습관: 지우기 전에 같은 경로로 `ls` 를 먼저 쳐본다.

```bash
ls -d ~/Desktop/kan     # 먼저 확인
rm -r ~/Desktop/kan     # 그다음 삭제
```

## 7. 리다이렉션과 파이프

터미널의 진짜 힘은 명령을 조합하는 데서 나온다.

### 표준 입출력 세 가지

| 이름 | 번호 | 용도 |
| :--- | :--- | :--- |
| stdin | 0 | 입력 |
| stdout | 1 | 정상 출력 |
| stderr | 2 | 에러 출력 |

```bash
command > out.txt        # stdout을 파일로
command 2> err.txt       # stderr를 파일로
command > all.txt 2>&1   # 둘 다 한 파일로
command 2>/dev/null      # 에러 메시지 버리기
```

`2>&1` 은 "stderr(2)를 stdout(1)이 가는 곳으로 보내라"는 뜻이다. 보고서의 실습 스크립트에서도 명령의 출력과 에러를 함께 잡으려고 이 표현을 썼다.

### 파이프

앞 명령의 출력을 뒤 명령의 입력으로 넘긴다.

```bash
docker info | grep "Server Version"
#            └─ docker info의 출력에서 해당 줄만 골라냄

docker images | head -5
ls -l | wc -l
```

보고서 7번의 `docker info | grep "Server Version"` 이 이 형태다. `docker info` 는 수십 줄을 뱉는데 그중 한 줄만 필요하므로 `grep` 으로 걸렀다.

## 8. 직접 해보기

아래를 순서대로 쳐 보고, 각 단계에서 `ls` 로 상태를 확인해 본다.

```bash
# 준비
cd ~/Desktop
mkdir practice && cd practice
pwd

# 파일 생성과 확인
echo "hello" > a.txt
cat a.txt
echo "world" >> a.txt
cat a.txt          # 두 줄이 나와야 한다

# 복사
cp a.txt b.txt
ls

# 이름 변경
mv b.txt c.txt
ls

# 디렉토리로 이동
mkdir sub
mv c.txt sub/
ls sub

# 디렉토리 이름 변경 후 삭제
mv sub sub-old
ls
rm -r sub-old
ls

# 정리
cd ~/Desktop
rm -r practice
ls -d practice     # "No such file or directory" 가 나오면 성공
```

**확인 문제**: `echo "x" > a.txt` 를 두 번 실행하면 `a.txt` 는 몇 줄인가? `>>` 로 두 번 하면?

<details>
<summary>답</summary>

`>` 는 매번 덮어쓰므로 **1줄**. `>>` 는 이어 붙이므로 **2줄**.
</details>

## 9. 자주 하는 실수

| 실수 | 증상 | 해결 |
| :--- | :--- | :--- |
| 공백 있는 파일명을 그냥 씀 | `rm my file.txt` → 두 파일을 지우려 함 | 따옴표로 감싼다: `rm "my file.txt"` |
| `>` 와 `>>` 혼동 | 로그가 매번 초기화됨 | 이어 쓸 때는 `>>` |
| `ls -l` 로 디렉토리 권한 확인 | 안의 파일 권한이 나옴 | `ls -ld` 를 쓴다 |
| `cd` 후 위치 착각 | 엉뚱한 곳에 파일 생성 | 작업 전 `pwd` 습관화 |
| `rm -rf` 를 홈에서 실행 | 복구 불가 | 실행 전 경로 재확인, `ls` 로 먼저 검증 |

### A. 루브릭 직결 문항

#### A-1. 절대 경로와 상대 경로를 어떤 상황에서 선택하는지 설명할 수 있는가?

**⚡ 30초 답변**

> 판단 기준은 한 줄로 정리됩니다. **실행 위치가 달라져도 같은 대상을 가리켜야 하면 절대 경로, 프로젝트를 통째로 옮겨도 따라와야 하면 상대 경로**입니다.

**상황별 적용 — 실습에서 쓴 예로 답한다**

| 상황 | 선택 | 이유 |
| :--- | :--- | :--- |
| Dockerfile `COPY index.html ...` | 상대 | 빌드 컨텍스트 기준. 클론 위치가 달라도 동작해야 함 |
| `docker build .` 의 컨텍스트 | 상대 | 현재 위치 기준 |
| 볼륨 마운트 `-v my-vol:/data` | 절대 | 컨테이너 내부 경로는 `/` 로 시작해야 함 |
| cron·스크립트의 파일 참조 | 절대 | 실행 시점의 작업 디렉토리를 예측할 수 없음 |
| 시스템 설정 파일 경로 | 절대 | 위치가 고정되어야 함 |

**왜 그런가 — 한 단계 더 들어가면**

> 상대 경로는 **현재 작업 디렉토리(cwd)** 를 기준으로 해석됩니다. 그래서 어디서 실행하느냐에 따라 가리키는 대상이 달라집니다. 대화형 셸에서는 내가 있는 위치를 아니까 편하지만, cron이나 스크립트는 실행 시점의 cwd가 무엇일지 보장되지 않습니다. 그래서 절대 경로를 씁니다.
>
> 반대로 Dockerfile의 `COPY` 에 절대 경로를 쓰면 제 컴퓨터에서만 빌드됩니다. 저장소는 누가 어디에 클론할지 모르니까요.

**📄 근거**: 보고서 **14-3** (상황별 선택 표) + **4번** (디렉토리 설계 기준)

#### A-2. 터미널로 폴더/파일을 생성·이동·삭제한 흔적이 있는가?

**⚡ 30초 답변**

> 보고서 5번에 전 과정이 실제 출력과 함께 있습니다. 생성은 `mkdir`·`echo >`, 확인은 `ls`·`cat`, 복사는 `cp`, 이동은 `mv`, 삭제는 파일 `rm`·디렉토리 `rm -r` 로 수행했습니다.
>
> 특히 `mv` 는 **같은 디렉토리에서 쓰면 이름 변경, 다른 디렉토리를 대상으로 쓰면 이동**이라 두 경우를 모두 기록했고, 파일과 디렉토리 양쪽에 적용해 네 가지 경우를 남겼습니다.

### B. 따라붙기 쉬운 후속 질문

#### B-1. `mv` 는 이동인가 이름 변경인가?

> 둘 다입니다. 파일시스템에서 두 작업이 **동일**하기 때문입니다. 경로(이름)를 다른 경로로 바꾸는 것이고, 같은 디스크 안이면 데이터를 옮기지 않고 이름표만 교체하므로 **파일 크기와 무관하게 즉시** 끝납니다.
>
> 다른 디스크로 옮길 때는 이야기가 다릅니다. 실제로 복사한 뒤 원본을 지우므로 크기에 비례해 시간이 걸립니다.

---

#### B-2. `cp` 와 `mv` 의 차이는?

> `cp` 는 원본을 남기고 사본을 만들고, `mv` 는 원본을 옮깁니다. 결과적으로 `cp` 는 파일이 2개, `mv` 는 1개가 됩니다.
>
> 성능 차이도 있습니다. `cp` 는 항상 데이터를 실제로 복사하지만, `mv` 는 같은 디스크 안에서는 이름표만 바꿔서 훨씬 빠릅니다.

---

#### B-3. 디렉토리를 지울 때 `-r` 이 왜 필요한가?

> 안전장치입니다. 디렉토리는 안에 무엇이 얼마나 들어 있는지 모른 채 지울 수 있어서, **재귀 삭제 의사를 명시적으로 표현**하게 만든 겁니다. `rm` 만 쓰면 `is a directory` 에러가 납니다.
>
> 빈 디렉토리만 지우는 `rmdir` 도 있는데, 안에 파일이 있으면 실패하므로 오히려 더 안전합니다.

---

#### B-4. `rm -rf` 가 위험한 이유는?

> `-r` 은 재귀, `-f` 는 강제(확인 없이, 없는 파일도 에러 없이)입니다. 둘을 합치면 **확인 절차가 전부 사라집니다.**
>
> 특히 위험한 패턴이 두 가지입니다. 변수를 쓸 때 값이 비면 `rm -rf $DIR/` 이 `rm -rf /` 가 됩니다. 그리고 경로 중간에 실수로 공백이 들어가면 의도한 것과 전혀 다른 대상이 지워집니다.
>
> 습관으로 삼을 만한 건 **지우기 전에 같은 경로로 `ls` 를 먼저 쳐 보는 것**입니다.

---

#### B-5. `>` 와 `>>` 의 차이는?

> `>` 는 덮어쓰기, `>>` 는 이어쓰기입니다. `>` 는 파일이 있으면 **내용을 통째로 날리고** 새로 씁니다. 로그를 남길 때 `>` 를 쓰면 매번 이전 내용이 사라집니다.

---

#### B-6. 숨김 파일은 어떻게 보나?

> `ls -a` 입니다. Unix 계열에서 이름이 `.` 으로 시작하면 숨김 파일로 취급됩니다. 특별한 속성이 있는 게 아니라 **이름 규칙**일 뿐입니다.
>
> 실습에서 다룬 `.env`, `.gitignore`, `.dockerignore` 가 전부 여기 해당합니다. `ls` 만 쳐서 "파일이 없네" 하고 넘어가면 안 되는 이유입니다.

---

#### B-7. `~`, `.`, `..`, `-` 는 각각 무엇인가?

| 기호 | 의미 | 예 |
| :--- | :--- | :--- |
| `~` | 홈 디렉토리 | `cd ~/Desktop` |
| `.` | 현재 디렉토리 | `docker build .` |
| `..` | 상위 디렉토리 | `cd ../..` |
| `-` | 직전 디렉토리 | `cd -` (왔던 곳으로 되돌아감) |

> `~` 는 셸이 홈 경로로 확장해 주는 것이라, 일부 설정 파일이나 프로그램에서는 그냥 문자로 취급돼 동작하지 않을 수 있습니다.

---

#### B-8. 파이프(`|`)와 리다이렉션(`>`)의 차이는?

> `>` 는 출력을 **파일**로 보내고, `|` 는 출력을 **다음 명령의 입력**으로 넘깁니다.
>
> ```bash
> docker info > out.txt              # 파일에 저장
> docker info | grep "Server"        # grep 에게 넘김
> ```
>
> 실습에서 `docker info | grep "Server Version"` 을 쓴 게 후자입니다. 긴 출력에서 필요한 줄만 뽑을 때 씁니다.

### C. 실전 시나리오

#### C-1. "파일이 안 지워집니다."

> 순서대로 확인합니다.
>
> 1. **디렉토리인가** — `rm` 만으로는 안 지워진다. `rm -r` 필요
> 2. **경로가 맞나** — `ls <경로>` 로 실재 확인
> 3. **권한이 있나** — 파일이 아니라 **그 파일이 든 디렉토리의 `w` 권한**이 필요하다 ([02번 문서](02-file-permissions.md) 참고)
> 4. **이름에 특수문자가 있나** — 공백이나 `-` 로 시작하는 이름은 따옴표로 묶거나 `rm -- <파일>` 로 처리

---

#### C-2. "명령을 쳤는데 아무 반응이 없습니다."

> Unix 철학상 **성공하면 아무 말도 하지 않습니다.** `mkdir`, `cp`, `mv`, `rm` 은 정상 동작하면 출력이 없습니다. 실습 로그에서 이 명령들 아래가 비어 있는 게 정상입니다.
>
> 확인하려면 결과를 조회하는 명령을 따로 칩니다.
>
> ```bash
> mkdir kan && ls -d kan       # 만들고 바로 확인
> echo $?                      # 직전 명령의 종료 코드 (0이면 성공)
> ```
