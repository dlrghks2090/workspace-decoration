# 11. 트러블슈팅 방법론

> 보고서 대응: [15번 트러블슈팅](../README.md), 16번 미션 회고

---

## 1. 왜 방법론이 필요한가

문제가 생기면 대개 이렇게 한다.

```
에러 발생 → 검색 → 나온 명령 복붙 → 안 됨 → 다른 명령 복붙 → ...
```

이 방식의 문제는 **고쳐져도 왜 고쳐졌는지 모른다**는 것이다. 같은 문제가 다시 나면 또 처음부터 헤맨다. 운 좋게 해결돼도 지식이 남지 않는다.

대안은 **가설을 세우고 검증하는 것**이다.

```
가설  →  확인  →  조치  →  결과
```

| 단계 | 하는 일 | 산출물 |
| :--- | :--- | :--- |
| **가설** | 원인이 무엇일지 추측 | "데몬이 안 떠 있을 것이다" |
| **확인** | 그 가설이 맞는지 검증할 명령 실행 | `docker info` 실패 확인 |
| **조치** | 가설에 근거한 해결 시도 | Docker Desktop 기동 |
| **결과** | 실제로 해결됐는지 확인 | `Server Version: 27.3.1` |

핵심은 **확인 단계**다. 가설을 세웠으면 바로 고치지 말고 먼저 검증한다. 검증 없이 고치면 우연히 해결됐는지 진짜 원인이었는지 구분할 수 없다.

## 2. 기본 원칙 5가지

### ① 에러 메시지를 끝까지 읽는다

에러 메시지는 대부분 답을 담고 있다. 보고서 15-2가 좋은 예다.

```
Bind for 0.0.0.0:8081 failed: port is already allocated.
      └────┬────┘                └──────┬──────┘
   어디서 실패했나              무엇이 문제인가
```

이 한 줄에서 알 수 있는 것:
- 문제는 **호스트 포트 8081** (컨테이너 내부가 아님)
- 원인은 **이미 점유됨** (권한 문제나 설정 오류가 아님)

에러를 읽지 않고 검색부터 하면 이 정보를 버리는 셈이다.

### ② 문제를 좁힌다

전체가 안 될 때는 **어디까지 되는지** 확인한다.

```
docker --version   → 성공   ┐
                            ├─ CLI는 정상, 데몬이 문제
docker info        → 실패   ┘
```

보고서 15-1의 진단이 정확히 이 구조다. 두 명령의 결과가 갈리는 지점이 문제의 경계다.

### ③ 입력이 아니라 출력을 검증한다

보고서 16번의 가장 큰 교훈이다.

```
템플릿 원본을 아무리 봐도 문제가 안 보인다
     ↓
렌더링된 결과를 열어보니 바로 보였다
```

설정 파일, 템플릿, 빌드 결과물은 **최종 산출물을 확인**해야 한다.

```bash
docker compose config                              # Compose 치환 결과
docker compose exec web cat /etc/nginx/conf.d/default.conf   # 컨테이너 안 결과
docker inspect my-app                              # 실제 적용된 설정
```

### ④ 최소 재현을 만든다

복잡한 상황에서 원인을 찾기 어려우면, 문제가 재현되는 **가장 작은 예제**를 만든다. 보고서 11번의 대조 실험이 이 방식이다.

```
볼륨 O → 데이터 유지
볼륨 X → 데이터 소실
        ↓
차이는 볼륨 하나뿐 → 원인 확정
```

변수를 하나만 다르게 한 두 실험을 나란히 놓으면 원인이 드러난다.

### ⑤ 로그를 본다

컨테이너가 죽었으면 왜 죽었는지 로그에 있다.

```bash
docker logs my-app
docker compose logs web
docker compose logs --tail 20 web
```

추측하기 전에 로그부터 보는 습관이 시간을 가장 많이 아낀다.

## 3. 실제 사례 6건 분석

보고서 15번에 기록된 사례들이다. 각각 어떤 사고 과정을 거쳤는지 뜯어본다.

### 사례 1 — Docker 데몬 미기동 (15-1)

```
Cannot connect to the Docker daemon at unix:///Users/****/.docker/run/docker.sock.
Is the docker daemon running?
```

| 단계 | 내용 |
| :--- | :--- |
| **가설** | `docker --version` 은 됐으므로 CLI 문제는 아니다. CLI와 데몬이 분리된 구조이니 데몬만 죽었을 것이다 |
| **확인** | `docker --version` → 성공 / `docker info` → 실패. 클라이언트는 살아 있고 서버가 없다 |
| **조치** | `open -a Docker` 로 Docker Desktop 기동 |
| **결과** | `docker info \| grep "Server Version"` → `Server Version: 27.3.1` |

**교훈**: `docker --version` 이 동작한다고 Docker를 쓸 수 있는 게 아니다. 설치 확인과 데몬 확인은 별개다.

**일반화**: 클라이언트-서버 구조의 도구는 항상 양쪽을 따로 확인한다. (DB 클라이언트가 깔려 있다고 DB 서버가 떠 있는 건 아니다.)

---

### 사례 2 — 호스트 포트 충돌 (15-2)

```
docker: Error response from daemon: driver failed programming external connectivity
on endpoint my-app2: Bind for 0.0.0.0:8081 failed: port is already allocated.
```

| 단계 | 내용 |
| :--- | :--- |
| **가설** | 에러가 `Bind for 0.0.0.0:8081` 이므로 호스트 포트 8081이 이미 점유됨 |
| **확인** | `lsof -i :8081` → Docker 프로세스가 LISTEN 중 / `docker ps` → `my-app` 이 8081 사용 |
| **조치** | 컨테이너 포트(80)는 두고 **호스트 포트만** 8082로 변경 |
| **결과** | 두 컨테이너가 8081, 8082로 공존. `curl -sI localhost:8082` → `200 OK` |

**교훈**: 고쳐야 할 것은 이미지도 컨테이너 포트도 아닌 **호스트 포트 하나**였다. 그리고 실패한 컨테이너도 생성은 되므로 재시도 전 `docker rm` 이 필요하다.

**진단 순서 일반화**:
```
1. 에러 메시지에서 어느 포트인지 확인
2. lsof -i :포트   → 점유 프로세스 식별
3. docker ps       → Docker 컨테이너인지 확인
4. 기존 것이 필요? → 새 호스트 포트 / 불필요? → 정리
5. curl 로 재검증
```

---

### 사례 3 — 컨테이너 삭제 후 데이터 소실 (15-3)

```
cat: /tmp/test.txt: No such file or directory
```

| 단계 | 내용 |
| :--- | :--- |
| **가설** | 파일을 컨테이너 쓰기 레이어에 썼기 때문에 컨테이너와 함께 사라졌을 것이다 |
| **확인** | 저장 위치만 볼륨으로 바꿔 재실험 → 컨테이너를 지워도 `saved` 가 남았다 |
| **조치** | 이름 있는 볼륨 사용 |
| **결과** | 대조표로 정리. 같은 이미지·같은 명령인데 저장 위치만 다르면 결과가 갈린다 |

**교훈**: 원인은 "컨테이너 삭제"라는 행위가 아니라 **"어디에 썼는가"** 였다. 대조군을 만들어서 이걸 증명했다.

**일반화**: "A를 했더니 B가 됐다"는 관찰만으로는 인과를 알 수 없다. A만 다르게 한 대조 실험이 있어야 한다.

---

### 사례 4 — envsubst가 주석까지 치환 (15-4)

템플릿에 쓴 주석이 결과물에서 깨졌다.

```nginx
# 작성한 것
# ${NGINX_PORT} 는 컨테이너 기동 시 환경 변수 값으로 치환된다.

# 결과물
# 8080 는 컨테이너 기동 시 환경 변수 값으로 치환된다.
```

| 단계 | 내용 |
| :--- | :--- |
| **가설(틀림)** | "설정 파일의 주석은 파서가 무시하니 치환 대상도 아닐 것이다" |
| **확인** | `docker compose exec web cat /etc/nginx/conf.d/default.conf` 로 **결과물**을 직접 열어보니 주석까지 치환돼 있었다 |
| **조치** | 주석에서 변수 표기를 제거하고 서술형으로 변경 |
| **결과** | 결과물의 주석이 정상 |

**교훈**: envsubst는 nginx 설정 문법을 이해하는 도구가 아니라 **단순 텍스트 치환기**다. "설정 파일이니 알아서 하겠지"라는 추측이 틀렸다.

**일반화**: **템플릿을 다룰 때는 입력이 아니라 출력을 검증한다.** 원본만 봐서는 안 보이는 문제가 있다.

---

### 사례 5 — SSH 공개키 형식 오류 (15-5)

```
Key is invalid. You must supply a key in OpenSSH public key format
```

| 단계 | 내용 |
| :--- | :--- |
| **가설 1** | 키 파일이 손상됐을 것이다 |
| **확인 1** | `ssh-keygen -lf` 가 지문을 정상 출력 → 파일은 유효한 OpenSSH 공개키. **가설 기각** |
| **가설 2** | 붙여넣은 내용이 공개키가 아닐 것이다 |
| **확인 2** | 등록 필드에 공개키 원문 대신 **지문**(`SHA256:...`)을 붙여넣었음을 확인 |
| **조치** | `pbcopy < ~/.ssh/id_ed25519.pub` 로 원문 재복사 후 등록 |
| **결과** | `ssh -T git@github.com` → `successfully authenticated` |

**교훈**: 공개키와 지문은 용도가 다르다. 지문은 **대조용**, 등록에는 **원문**이 필요하다.

**일반화**: 첫 가설이 틀리는 건 정상이다. 중요한 건 **기각할 수 있는 형태로 가설을 세우는 것**이다. "파일이 손상됐다"는 `ssh-keygen -lf` 한 번으로 검증 가능한 가설이었기에 빠르게 다음으로 넘어갈 수 있었다.

---

### 사례 6 — 종료된 컨테이너에 exec 불가 (16번 회고)

```
Error response from daemon: container 88b72e13f017... is not running
```

| 단계 | 내용 |
| :--- | :--- |
| **가설** | 컨테이너가 이미 종료 상태라 exec가 붙을 프로세스가 없을 것이다 |
| **확인** | `docker ps -a` 에서 `Exited (0)` 확인. `sh -c "echo ..."` 는 즉시 끝나는 명령이라 컨테이너도 곧바로 종료 |
| **조치** | `docker run -d --name novol-test ubuntu sleep 300` 으로 살려둔 뒤 exec |
| **결과** | 실험 성공 |

**교훈**: **컨테이너의 수명 = PID 1 프로세스의 수명.** 컨테이너는 "켜 두는 상자"가 아니라 "프로세스를 감싼 것"이다.

### [참고] Linux 전용 — Docker 소켓 권한 거부

이번 실습 환경은 macOS라 **겪지 않은 사례**다. 보고서(README)는 실제로 겪은 사례만 싣는 원칙이라 여기에 참고로 옮겨 둔다. Linux 환경에서는 가장 흔하게 만나는 Docker 첫 에러다.

```
permission denied while trying to connect to the Docker daemon socket
at unix:///var/run/docker.sock
```

**원인**: Linux에서 Docker 소켓 `/var/run/docker.sock` 은 `root:docker` 소유이며 권한이 `srw-rw----` 다. `docker` 그룹에 속하지 않은 사용자는 읽기·쓰기가 막힌다.

```bash
ls -l /var/run/docker.sock
# srw-rw---- 1 root docker 0 ... /var/run/docker.sock
```

**조치**:

```bash
sudo usermod -aG docker $USER
```

그룹 변경은 **새 로그인 세션부터** 적용된다. 로그아웃 후 재로그인하거나 `newgrp docker` 로 현재 셸에 즉시 반영한다. `id -nG` 에 `docker` 가 보이는지로 확인한다.

**15-1(데몬 미기동)과 구분하는 법** — 에러 문구가 다르다.

| 에러 문구 | 원인 | 조치 |
| :--- | :--- | :--- |
| `Cannot connect to the Docker daemon` | 데몬이 **꺼져 있음** | 데몬 기동 (macOS는 `open -a Docker`) |
| `permission denied ... docker.sock` | 데몬은 떠 있으나 **접근 권한 없음** | `docker` 그룹에 사용자 추가 (Linux) |

**macOS에서 발생하지 않는 이유**: Docker Desktop은 소켓을 시스템 경로가 아니라 사용자 홈 아래(`~/.docker/run/docker.sock`)에 둔다. 소유자가 곧 사용자 본인이므로 그룹 권한 문제가 생기지 않는다. macOS에서는 15-1의 "데몬이 꺼져 있음"이 압도적으로 흔한 원인이다.

> **보안 참고**: `docker` 그룹 가입은 사실상 root 권한을 주는 것과 같다. 호스트 루트를 컨테이너에 마운트하면 무엇이든 할 수 있기 때문이다. 편의를 위해 넣되, 다중 사용자 서버에서는 아무에게나 부여하면 안 된다.

## 4. 상황별 진단 체크리스트

### Docker 명령이 전부 실패할 때

```bash
docker --version          # CLI 설치 확인
docker info               # 데몬 확인 ← 여기서 실패하면 데몬 문제
open -a Docker            # macOS 기동
```

### 컨테이너가 바로 죽을 때

```bash
docker ps -a              # Exit code 확인
docker logs <이름>        # 왜 죽었는지
docker inspect <이름> --format '{{.State.ExitCode}} {{.State.Error}}'
```

| Exit code | 의미 |
| :--- | :--- |
| 0 | 정상 종료 (명령이 끝남 — 컨테이너 수명 문제) |
| 1 | 애플리케이션 에러 |
| 125 | Docker 데몬 자체 오류 |
| 126 | 명령을 실행할 수 없음 (권한 등) |
| 127 | 명령을 찾을 수 없음 (경로 오타) |
| 137 | SIGKILL (OOM 등 강제 종료) |

### 접속이 안 될 때

```bash
docker ps                             # 컨테이너가 떠 있나
docker port <이름>                    # 포트 매핑 확인
docker logs <이름>                    # 앱이 정상 기동했나
docker exec <이름> curl localhost:80  # 컨테이너 안에서는 되나
lsof -i :8081                         # 호스트 포트 점유 확인
```

**컨테이너 안에서는 되는데 밖에서 안 되면** → 포트 매핑 문제
**컨테이너 안에서도 안 되면** → 애플리케이션 문제

### 빌드가 실패할 때

```bash
docker build --progress=plain -t test .    # 전체 로그 출력
docker build --no-cache -t test .          # 캐시 무시
```

`COPY` 실패는 대부분 **빌드 컨텍스트 밖의 파일**을 참조했거나 경로 오타다.

### Compose가 이상할 때

```bash
docker compose config      # 변수 치환 결과 + 문법 검증
docker compose ps -a       # 종료된 서비스까지
docker compose logs <서비스>
docker compose up -d --build   # 이미지 변경이 반영 안 될 때
```

### Git/SSH가 안 될 때

```bash
git remote -v                       # URL 형식 (HTTPS? SSH?)
ssh -T git@github.com               # 인증 확인
ssh -v -T git@github.com            # 상세 로그
ssh-add -l                          # agent에 키가 있나
ls -l ~/.ssh/id_ed25519             # 권한 600인가
```

## 5. 기록하는 법

해결하고 끝내면 다음에 또 헤맨다. 기록의 최소 단위는 이렇다.

```markdown
### 문제 제목

- **현상**: (에러 메시지 원문 그대로)
- **가설**: 무엇이 원인이라고 생각했나
- **확인**: 그 가설을 어떻게 검증했나 (명령 + 출력)
- **조치**: 무엇을 했나
- **결과**: 해결됐다는 증거 (명령 + 출력)
- **배운 점**: 다음에 비슷한 상황에서 쓸 수 있는 일반화
```

### 좋은 기록의 조건

| 항목 | 이유 |
| :--- | :--- |
| 에러 메시지를 원문 그대로 | 나중에 검색해서 찾을 수 있다 |
| 실행한 명령과 출력을 함께 | 재현 가능해진다 |
| 틀린 가설도 기록 | "이건 원인이 아니다"도 정보다 |
| 일반화 한 줄 | 다른 상황에 적용할 수 있다 |

보고서 15-5에서 "가설 1이 기각됨"을 그대로 남긴 이유다. 파일이 정상이라는 사실을 확인한 것 자체가 진단 과정의 일부다.

## 6. 직접 해보기

각 문제를 **일부러 만들어** 놓고 진단해 본다. 답을 보기 전에 스스로 가설을 세워볼 것.

```bash
# ===== 문제 1: 컨테이너가 즉시 종료 =====
docker run --name p1 ubuntu
docker ps -a --filter name=p1
# 가설을 세우고 → docker logs p1, exit code 확인 → 원인 파악
docker rm p1

# ===== 문제 2: 포트 충돌 =====
docker run -d -p 7777:80 --name p2a nginx
docker run -d -p 7777:80 --name p2b nginx
# 에러 메시지를 끝까지 읽고 → lsof -i :7777 → 해결
docker rm -f p2a p2b 2>/dev/null

# ===== 문제 3: 접속 불가 =====
docker run -d --name p3 nginx          # -p 없음
curl --max-time 3 localhost:7778
# docker port p3 → 왜 안 되는지 설명해 보기
docker exec p3 curl -s localhost:80    # 안에서는 되나?
docker rm -f p3

# ===== 문제 4: 변경이 반영 안 됨 =====
mkdir ~/Desktop/ts && cd ~/Desktop/ts
echo '<h1>v1</h1>' > index.html
printf 'FROM nginx\nCOPY index.html /usr/share/nginx/html/index.html\n' > Dockerfile
printf 'services:\n  web:\n    build: .\n    image: ts:v1\n    ports:\n      - "7779:80"\n' > docker-compose.yml
docker compose up -d
curl -s localhost:7779
echo '<h1>v2</h1>' > index.html
docker compose up -d
curl -s localhost:7779                 # 왜 v1 그대로인가?
docker compose up -d --build
curl -s localhost:7779                 # 이제 v2
docker compose down && docker rmi ts:v1
cd ~/Desktop && rm -r ts

# ===== 문제 5: 데이터 소실 =====
docker run -d --name p5 ubuntu sleep 60
docker exec p5 sh -c "echo data > /tmp/x.txt"
docker rm -f p5
docker run --rm ubuntu cat /tmp/x.txt  # 왜 없나? 어떻게 방지하나?
```

<details>
<summary>답</summary>

1. `ubuntu` 의 기본 명령은 `bash` 인데 `-it` 없이 실행하면 입력이 없어 즉시 끝난다. 컨테이너 수명 = PID 1 수명이므로 컨테이너도 종료. Exit code 0(정상 종료)이 단서다.
2. 호스트 포트 7777이 이미 점유됨. `p2b` 의 호스트 포트만 다른 값으로 바꾸면 된다. 실패한 `p2b` 컨테이너를 먼저 `rm` 해야 이름 충돌을 피한다.
3. `-p` 옵션이 없어 포트 매핑이 안 됐다. 컨테이너 안에서는 정상 동작하므로 애플리케이션 문제가 아니라 매핑 문제로 좁혀진다.
4. `docker compose up` 은 기존 이미지를 재사용한다. `COPY` 대상 파일이 바뀌어도 자동 재빌드하지 않으므로 `--build` 가 필요하다.
5. `/tmp` 는 컨테이너 쓰기 레이어라 컨테이너 삭제와 함께 사라졌다. 볼륨(`-v vol:/data`)에 저장하면 유지된다.
</details>

### A. 루브릭 직결 문항

#### A-1. 이 미션에서 가장 어려웠던 지점과, 해결 과정(가설 → 확인 → 조치)을 근거와 함께 설명할 수 있는가?

**⚡ 답변 — 4단계를 순서대로 밟는다**

> **가장 어려웠던 건 환경 변수 치환의 동작 범위를 잘못 예상한 것**이었습니다.
>
> **[현상]** 보너스 4에서 nginx 템플릿에 포트를 환경 변수로 넣고 옆에 설명 주석을 달았는데, 컨테이너 안의 결과 파일에서 주석 문장이 깨져 있었습니다. `# ${NGINX_PORT} 는 ... 치환된다` 라고 쓴 게 `# 8080 는 ... 치환된다` 가 되어 문장이 성립하지 않았습니다.
>
> **[가설]** 처음엔 "설정 파일의 주석은 파서가 무시하니까 치환 대상도 아닐 것"이라고 생각했습니다. 그래서 다른 원인을 찾으려 했습니다.
>
> **[확인]** 템플릿 원본만 봐서는 문제가 안 보였습니다. 그래서 컨테이너 안의 **결과물**을 직접 열었습니다.
>
> ```bash
> docker compose exec web cat /etc/nginx/conf.d/default.conf
> ```
>
> 열어 보니 주석까지 치환돼 있었습니다. **제 가설이 틀린 겁니다.**
>
> **[조치]** 주석에서 변수 표기를 빼고 서술형으로 바꿨습니다.
>
> **[근거와 교훈]** 원인은 envsubst가 nginx 설정 문법을 이해하는 도구가 아니라 **단순 텍스트 치환기**라는 점이었습니다. `${...}` 패턴이 보이면 주석이든 아니든 무조건 바꿉니다. "설정 파일이니 파서가 알아서 하겠지"라는 추측이 틀렸던 거죠.
>
> 여기서 배운 건 **템플릿을 다룰 때는 입력이 아니라 출력을 검증해야 한다**는 것입니다.

**두 번째 사례도 준비해 둔다** (하나 더 물으면)

> 볼륨 대조 실험을 짤 때 `docker exec` 가 붙지 않았습니다. `container ... is not running` 이었는데, 가설은 "컨테이너가 이미 종료돼서 exec가 붙을 프로세스가 없다"였고, `docker ps -a` 에서 `Exited (0)` 을 확인했습니다. `sh -c "echo ..."` 는 즉시 끝나는 명령이라 컨테이너도 곧바로 종료된 겁니다.
>
> `sleep 300` 으로 살려 둔 뒤 실험을 재설계해서 해결했고, **컨테이너의 수명은 PID 1 프로세스의 수명과 같다**는 걸 실감했습니다. 컨테이너는 켜 두는 상자가 아니라 프로세스를 감싼 것이더군요.

**📄 근거**: 보고서 **16번 미션 회고** + **15-4**

**⚠️ 이 항목에서 감점되는 패턴**

| 하면 안 되는 답 | 왜 감점인가 |
| :--- | :--- |
| "다 잘 됐습니다" | 어려움이 없었다 = 깊이 안 해봤다는 신호 |
| "구글에서 찾아서 고쳤습니다" | 사고 과정이 없다 |
| 결론만 말하기 | 가설·확인 단계가 빠지면 운으로 해결한 것과 구분 안 됨 |
| 틀린 가설을 숨기기 | **오히려 반대다.** 기각 과정이 있어야 검증을 했다는 증거가 된다 |

#### A-2. 문제 해결 시 어떤 순서로 접근하나?

**⚡ 답변 — 5단계**

> ① **에러 메시지를 끝까지 읽어** 문제 지점을 특정합니다. 대부분 답이 그 안에 있습니다.
> ② **어디까지 정상인지 확인해** 범위를 좁힙니다.
> ③ **검증 가능한 가설**을 세웁니다.
> ④ **고치기 전에 가설을 먼저 확인**합니다.
> ⑤ 조치 후 **결과를 증거로 확인**합니다.
>
> ④가 핵심입니다. **검증 단계를 건너뛰면 우연히 해결됐는지 진짜 원인이었는지 구분할 수 없습니다.** 그러면 같은 문제가 다시 나왔을 때 또 처음부터 헤맵니다.

**②의 실례를 들면**

> 실습에서 Docker 명령이 전부 실패했을 때, `docker --version` 은 성공하는데 `docker info` 만 실패했습니다. 두 명령의 결과가 갈리는 지점이 문제의 경계였고, CLI는 정상이고 데몬이 죽었다는 걸 바로 알 수 있었습니다.

#### A-3. 인과관계를 어떻게 확인하나?

**⚡ 30초 답변**

> **변수를 하나만 다르게 한 대조 실험**을 만듭니다.
>
> 볼륨 실습에서 같은 이미지·같은 명령으로 저장 위치만 볼륨과 쓰기 레이어로 나눠 실행했더니, 데이터 소실의 원인이 **컨테이너 삭제라는 행위가 아니라 저장 위치**라는 게 드러났습니다.
>
> "A를 했더니 B가 됐다"는 관찰만으로는 상관관계까지만 알 수 있습니다. A만 다르게 한 대조군이 있어야 인과를 말할 수 있습니다.

| 저장 위치 | 컨테이너 삭제 후 |
| :--- | :--- |
| 쓰기 레이어 | 소실 |
| 볼륨 | 유지 |

> 이 표 한 장이 "볼륨을 쓰면 됩니다"보다 훨씬 강한 근거입니다.

### B. 따라붙기 쉬운 후속 질문

#### B-1. 에러 메시지에서 무엇을 읽나?

```
Bind for 0.0.0.0:8081 failed: port is already allocated.
      └────┬────┘                └──────┬──────┘
   어디서 실패했나              무엇이 문제인가
```

> **위치와 원인을 분리해서 읽습니다.** 이 한 줄에서 "호스트 포트 8081"(컨테이너 내부가 아님)과 "이미 점유됨"(권한이나 설정 오류가 아님)이 동시에 확정됩니다.
>
> 에러를 읽지 않고 검색부터 하면 이 정보를 버리는 셈입니다.

---

#### B-2. "문제를 좁힌다"는 게 구체적으로 무엇인가?

> **어디까지 되는지** 확인해서 정상 구간과 비정상 구간의 경계를 찾는 것입니다.
>
> 예를 들어 웹 접속이 안 될 때 이렇게 좁힙니다.
>
> ```bash
> docker ps                              # 컨테이너가 떠 있나
> docker logs <이름>                     # 앱이 기동했나
> docker exec <이름> curl localhost:80   # 안에서는 되나
> curl localhost:8081                    # 밖에서는 되나
> ```
>
> **안에서 되는데 밖에서 안 되면 포트 매핑 문제**, **안에서도 안 되면 애플리케이션 문제**입니다. 한 번의 분기로 범위가 절반이 됩니다.

---

#### B-3. "입력이 아니라 출력을 검증한다"는 게 무슨 뜻인가?

> 설정 파일, 템플릿, 빌드 결과물은 **원본이 아니라 최종 산출물**을 봐야 한다는 뜻입니다.
>
> ```bash
> docker compose config                                       # 변수 치환 결과
> docker compose exec web cat /etc/nginx/conf.d/default.conf  # 컨테이너 안 결과
> docker inspect my-app                                       # 실제 적용된 설정
> ```
>
> envsubst 사례가 정확히 이 경우였습니다. 템플릿을 아무리 들여다봐도 문제가 안 보였는데, 렌더링된 결과를 열자 바로 보였습니다.

---

#### B-4. 최소 재현이 왜 중요한가?

> 복잡한 상황에서는 무엇이 원인인지 알 수 없습니다. **문제가 재현되는 가장 작은 예제**를 만들면 변수가 줄어 원인이 드러납니다.
>
> 부수 효과도 있습니다. 남에게 도움을 청할 때 최소 재현 예제가 있으면 훨씬 빨리 답을 받습니다.

---

#### B-5. 컨테이너 Exit code는 어떻게 읽나?

| Exit code | 의미 |
| :--- | :--- |
| 0 | 정상 종료 — **에러가 아니다.** 명령이 끝난 것 |
| 1 | 애플리케이션 에러 |
| 125 | Docker 데몬 자체 오류 |
| 126 | 명령을 실행할 수 없음 (권한 등) |
| 127 | 명령을 찾을 수 없음 (경로 오타) |
| 137 | 강제 종료 (OOM 등) |

> **0을 에러로 오해하는 경우가 많습니다.** 할 일을 다 하고 끝난 것이므로, "왜 죽었나"가 아니라 "무슨 프로세스를 돌리려 했나"를 봐야 합니다.

---

#### B-6. 기록을 왜 남기나? 고쳤으면 된 것 아닌가?

> 고치고 끝내면 **다음에 또 헤맵니다.** 특히 몇 달 뒤 같은 문제를 만나면 처음부터 다시 시작합니다.
>
> 최소 단위는 이렇습니다.
>
> - **현상** — 에러 메시지 원문 그대로 (나중에 검색으로 찾을 수 있게)
> - **가설** — 무엇이 원인이라고 생각했나
> - **확인** — 어떻게 검증했나 (명령 + 출력)
> - **조치** — 무엇을 했나
> - **결과** — 해결됐다는 증거
> - **배운 점** — 다른 상황에도 적용할 수 있는 일반화
>
> **틀린 가설도 기록합니다.** "이건 원인이 아니다"도 정보입니다. 보고서 15-5에서 "가설 1 기각"을 그대로 남긴 이유입니다.

### C. 실전 시나리오 — 상황별 첫 명령

#### C-1. Docker 명령이 전부 실패

docker --version    # CLI 확인
docker info         # 데몬 확인 ← 여기서 갈린다
open -a Docker      # macOS 기동

```bash
docker ps                              # 떠 있나

| 템플릿·설정 | 입력이 아니라 **출력**을 본다 |
| 인과 확인 | 변수 하나만 바꾼 **대조 실험** |
| Exit code 0 | 에러가 아니라 정상 종료 |
| 기록 | 틀린 가설도 남긴다 |
