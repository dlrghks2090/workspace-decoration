```bash
# 1. Docker 데몬 살아 있는지 (꺼져 있으면 실연이 전부 막힌다)

# 3. 실연용 이미지가 남아 있는지

# 5. 포트 8081 비어 있는지
```

## 1-1. 터미널에서 기본 명령어로 폴더/파일 생성·이동·삭제를 수행한 흔적이 있는가?

**⚡ 30초 답변**
> 보고서 5번에 전 과정이 실제 출력과 함께 있습니다. 생성은 `mkdir`·`echo >`, 확인은 `ls`·`cat`, 복사는 `cp`, 이동은 `mv`, 삭제는 파일 `rm`·디렉토리 `rm -r` 로 수행했습니다. 특히 `mv` 는 **같은 디렉토리에서 쓰면 이름 변경, 다른 디렉토리를 대상으로 쓰면 이동**이라 두 경우를 모두 기록했고, 파일과 디렉토리 양쪽에 적용해 네 가지 경우를 남겼습니다.

**📄 증거 위치**: 보고서 **5번 터미널 조작 로그 기록**

**💻 실연 명령**

```bash
cd ~/Desktop && mkdir demo && cd demo
echo "test" > a.txt && ls        # 생성
cp a.txt b.txt && ls             # 복사
mv a.txt c.txt && ls             # 이름 변경
mkdir sub && mv c.txt sub/ && ls sub    # 디렉토리로 이동
rm b.txt && ls                   # 파일 삭제
rm -r sub && ls                  # 디렉토리 삭제
cd ~/Desktop && rm -r demo
```

**꼬리질문 대비**
- *"`rm` 과 `rm -r` 의 차이는?"* → `rm` 은 파일만 지운다. 디렉토리는 안에 파일이 있을 수 있어 실수 방지를 위해 `-r`(recursive)을 명시해야 지워진다.
- *"`mv` 와 `cp` 의 차이는?"* → `cp` 는 원본을 남기고 복사본을 만들고, `mv` 는 원본을 옮긴다. `mv` 는 같은 파일시스템 안에서는 실제 데이터 이동 없이 이름표만 바꾸므로 훨씬 빠르다.

## 1-2. 파일 권한 변경 결과가 확인되는가?

**⚡ 30초 답변**
> 보고서 6번에 **변경 전후를 `ls -l` 로 실측**해 기록했습니다. `note.txt` 는 `-rw-r--r--`(644)에서 `chmod 600` 후 `-rw-------`(600)으로, `workspace` 디렉토리는 `drwxr-xr-x`(755)에서 `chmod 700` 후 `drwx------`(700)으로 바뀐 것을 확인했습니다. 전달한 숫자와 돌아온 문자 표기가 대응한다는 것이 출력으로 증명됩니다.

**📄 증거 위치**: 보고서 **6번 권한 실습 및 증거 기록** (전후 비교표 포함)

**💻 실연 명령**

```bash
cd ~/Desktop && mkdir perm && cd perm
echo "x" > note.txt && mkdir workspace
ls -l note.txt; ls -ld workspace       # 변경 전
chmod 600 note.txt; chmod 700 workspace
ls -l note.txt; ls -ld workspace       # 변경 후
cd ~/Desktop && rm -r perm
```

## 1-3. `docker --version` 이 출력되고, Docker가 동작 가능한 상태인가?

**⚡ 30초 답변**
> 보고서 7번에 있습니다. 다만 **`docker --version` 만으로는 동작 가능 여부를 알 수 없습니다.** Docker는 CLI와 데몬이 분리된 구조라, 버전 출력은 CLI 혼자 할 수 있지만 실제 작업은 데몬이 합니다. 그래서 `docker version` 까지 확인했습니다. 이 명령은 Client 정보를 찍은 뒤 **데몬에 질의해** Server 섹션을 채우므로, `Server:` 가 출력됐다는 것 자체가 데몬이 응답했다는 증거입니다. 실제로 실습 중 CLI는 정상인데 데몬이 꺼져 있어 실패한 사례를 15-1에 기록했습니다.

**📄 증거 위치**: 보고서 **7번** + **15-1 트러블슈팅**

**💻 실연 명령**

```bash
docker --version   # CLI 만 확인. 데몬이 꺼져 있어도 성공한다
docker version     # Server 블록이 나오면 데몬까지 확인된 것
```

보고서 7번에 있는 두 명령 그대로다. `docker info` 를 따로 칠 필요가 없다 — `docker version` 이 이미 데몬에 질의하기 때문이다.

**이 답변이 강한 이유**: 질문이 "출력되고, **동작 가능한 상태인가**"로 두 가지를 묻는다. 둘을 구분해 답하면 이해도가 드러난다. 특히 **`docker --version` 과 `docker version` 이 다른 명령**이라는 것, 앞의 것은 데몬에 접속조차 하지 않아 근거가 못 된다는 것을 짚으면 확실하다.

**꼬리질문 대비**
- *"macOS에서 `systemctl status docker` 는?"* → 안 된다. `systemctl` 은 systemd 기반 Linux 전용이다. macOS는 Docker Desktop 앱이 리눅스 VM 안의 데몬을 관리한다. `docker version` 출력에서 Client가 `darwin/arm64`, Server가 `linux/arm64` 로 갈리는 게 그 증거다.

## 1-4. `docker run hello-world` 가 정상 실행되는가?

**⚡ 30초 답변**
> 보고서 9번에 **출력 전문**이 있습니다. `Hello from Docker!` 메시지와 함께, 로컬에 이미지가 없어서(`Unable to find image ... locally`) 자동으로 레지스트리에서 받아온 뒤 실행되는 과정까지 기록했습니다.

**📄 증거 위치**: 보고서 **9번 컨테이너 실행 실습**

**💻 실연 명령**

```bash
docker run hello-world
```

**꼬리질문 대비**
- *"hello-world가 하는 일은?"* → Docker 설치가 제대로 됐는지 확인하는 최소 이미지다. 출력 메시지 자체가 "클라이언트가 데몬에 요청 → 데몬이 이미지를 받아옴 → 컨테이너 생성 → 출력 스트리밍"이라는 동작 흐름을 설명해 준다.
- *"실행 후 컨테이너는?"* → 메시지 출력 후 즉시 종료되지만 삭제되지는 않는다. `docker ps -a` 에 `Exited` 상태로 남는다. 보고서 8번의 `jolly_elgamal` 이 그것이다.

## 1-5. 이미지/컨테이너 목록 확인 및 정리 흔적이 있는가?

**⚡ 30초 답변**
> 보고서 8번에 조회부터 정리까지 전 과정이 있습니다. `docker pull` 로 받고 `docker images` 로 목록을 확인했고, `docker ps` / `docker ps -a` 로 실행 중인 것과 종료된 것을 구분했습니다. `docker logs` 로 로그를 확인했고, 정리는 `docker stop` → `docker rm` 순으로 수행한 뒤 목록이 비는 것까지 출력으로 남겼습니다.

**📄 증거 위치**: 보고서 **8번 Docker 기본 운영**

**💻 실연 명령**

```bash
docker images
docker ps          # 실행 중
docker ps -a       # 종료된 것까지
docker volume ls
```

**꼬리질문 대비**
- *"`ps` 와 `ps -a` 의 차이는?"* → `ps` 는 실행 중인 컨테이너만 보여준다. 종료된 컨테이너도 삭제 전까지 남아 있으므로 `-a` 로 확인해야 한다. 이걸 놓치면 "컨테이너가 없는데 이름이 중복된다"는 상황을 만난다.
- *"`stop` 과 `rm` 의 차이는?"* → `stop` 은 프로세스를 멈출 뿐 컨테이너와 쓰기 레이어는 남는다. `rm` 이 실제로 삭제하며 이때 쓰기 레이어의 데이터가 사라진다.

## 1-6. Dockerfile로 이미지 빌드가 가능한가?

**⚡ 30초 답변**
> 저장소 루트에 Dockerfile이 있고, 보고서 10번에 빌드 로그가 있습니다. `nginx:latest` 를 베이스로 `index.html` 과 nginx 설정 템플릿을 `COPY` 하고, `ENV` 로 포트 기본값을 넣었습니다. `docker build -t my-web:v1 .` 로 빌드했고 로그에서 3개 레이어가 순서대로 쌓이는 것을 확인할 수 있습니다.

**📄 증거 위치**: 보고서 **10번** + 저장소의 [`Dockerfile`](../Dockerfile)

**💻 실연 명령**

```bash
cat Dockerfile
docker build -t my-web:v1 .
docker images my-web
```

**꼬리질문 대비**
- *"`docker build .` 의 점(`.`)은?"* → 빌드 컨텍스트다. 이 경로의 파일들이 데몬에 전송되고, `COPY` 의 상대 경로가 여기를 기준으로 해석된다. 컨텍스트 밖의 파일은 `COPY` 할 수 없다.
- *"`EXPOSE` 를 쓰면 포트가 열리나?"* → 아니다. 문서화 목적일 뿐이고 실제 공개는 `-p` 나 Compose의 `ports:` 가 한다.
- *"왜 `ENV NGINX_PORT=80` 을 넣었나?"* → 안전망이다. Compose 없이 `docker run` 만 할 때 변수가 비면 nginx 설정이 `listen ;` 이 되어 기동에 실패한다.

## 1-7. 매핑된 포트로 접속이 가능한가?

**⚡ 30초 답변**
> 보고서 10번에 있습니다. `docker run -d -p 8081:80` 으로 띄우고 `curl -sI localhost:8081` 로 `HTTP/1.1 200 OK` 를 받았습니다. 헤더만이 아니라 본문도 확인했는데 `<h1>hello, world!</h1>` 가 나왔습니다. **이건 저장소의 `index.html` 내용과 일치하므로, 기본 nginx 페이지가 아니라 `COPY` 한 우리 파일이 서빙되고 있다는 증거**입니다.

**📄 증거 위치**: 보고서 **10번** (200 OK + 본문)

**💻 실연 명령**

```bash
docker run -d -p 8081:80 --name demo my-web:v1
sleep 2
curl -sI localhost:8081 | head -3
curl -s localhost:8081
docker rm -f demo
```

**이 답변이 강한 이유**: 200 OK만 보여주면 "서버가 떴다"까지만 증명된다. 본문까지 확인하면 **빌드한 이미지가 의도한 내용을 서빙한다**는 것까지 증명된다.

## 1-8. Docker 볼륨 데이터가 컨테이너 삭제 후에도 유지되는가?

**⚡ 30초 답변**
> 보고서 11번에 있습니다. 볼륨 생성 → 데이터 저장 → **컨테이너를 명시적으로 `docker rm` 으로 삭제** → 삭제됐는지 목록으로 확인 → 완전히 새 컨테이너로 읽기 순으로 진행해 `saved` 가 그대로 나오는 것을 확인했습니다. 삭제 단계를 명시적으로 넣어야 "삭제 후에도 유지"가 증명되기 때문입니다. 추가로 **볼륨을 쓰지 않은 대조군**도 만들어서, 같은 조건에서 저장 위치만 다르면 데이터가 사라지는 것을 나란히 기록했습니다.

**📄 증거 위치**: 보고서 **11번** (실험군 + 대조군 + 비교표)

**💻 실연 명령**

```bash
docker volume create demo-vol
docker run --name vt -v demo-vol:/data ubuntu sh -c "echo saved > /data/t.txt"
docker rm vt                                    # 컨테이너 삭제
docker run --rm -v demo-vol:/data ubuntu cat /data/t.txt
# saved                                         ← 살아남음
docker volume rm demo-vol
```

**이 답변이 강한 이유**: 대조 실험이 있으면 "볼륨을 썼더니 됐다"가 아니라 **"데이터 소실의 원인은 컨테이너 삭제라는 행위가 아니라 저장 위치"** 라는 인과를 증명한 것이 된다.

## 1-9. Git 설정 및 GitHub 연동이 확인되는가?

**⚡ 30초 답변**

**💻 실연 명령**

```bash
git config --list | grep -E "^user\.|^remote\."
git remote -v
git branch -vv
git log --oneline -5
git status -sb | head -1
```

**꼬리질문 대비**
- *"12번은 HTTPS인데 지금은 SSH다. 왜 다른가?"* → 12번은 그 시점의 실제 기록이고, 17-5에서 SSH로 전환했다. 시점이 다른 실제 출력이라 고치지 않고 그대로 뒀으며 17-5에 전환 사실을 명시했다.

## 2-1. 프로젝트 디렉토리 구조를 어떤 기준으로 구성했는지 설명할 수 있는가?

**⚡ 30초 답변**
> 세 가지 기준으로 정했습니다.
>
> **첫째, 빌드에 필요한 파일은 저장소 루트에 평평하게 뒀습니다.** `docker build .` 의 빌드 컨텍스트가 곧 저장소 루트가 되므로 Dockerfile 안에서 `COPY index.html` 처럼 짧은 상대 경로만 쓰면 됩니다. 하위 디렉토리로 나누면 경로가 길어지고 빌드 컨텍스트를 바꿀 때마다 Dockerfile도 고쳐야 합니다. 파일이 8개뿐인 규모에서는 계층을 만드는 비용이 이득보다 크다고 판단했습니다.
>
> **둘째, 실습 산출물은 저장소 밖에 격리했습니다.** 터미널·권한 실습 파일은 `~/Desktop/kan` 에서 작업하고 끝나고 지웠습니다. 저장소 안에서 하면 임시 파일이 `git status` 에 섞여 실제 산출물과 구분이 안 됩니다.
>
> **셋째, 설정과 코드를 분리했습니다.** 포트 같은 실행 설정은 `.env` 로 빼고 저장소에는 `.env.example` 만 커밋했습니다. 덕분에 이미지 재빌드 없이 설정만 바꿔 동작을 바꿀 수 있고, 실제 값이 저장소에 올라가지 않습니다.

**📄 증거 위치**: 보고서 **4번 프로젝트 디렉토리 구조 및 설계 기준**

**💻 실연 명령**

```bash
ls -a
cat Dockerfile | grep COPY      # 상대 경로 확인
git check-ignore -v .env        # .env 제외 확인
```

**꼬리질문 대비**
- *"규모가 커지면?"* → `src/`, `config/`, `docker/` 로 나눈다. 그때는 `build.context` 와 `dockerfile` 경로를 Compose에서 명시하게 된다. 지금은 파일 8개라 계층이 오히려 탐색 비용만 늘린다.
- *"`doc/` 는 왜 있나?"* → 보고서를 이해하기 위한 학습 자료다. 평가 대상인 `README.md` 와 구분하려고 별도 디렉토리로 뒀다.

## 2-2. 포트/볼륨 설정을 어떤 방식으로 재현 가능하게 정리했는지 설명할 수 있는가?

**⚡ 30초 답변**
> 보고서 13번에 표와 명령 시퀀스로 고정해 뒀습니다.
>
> **포트는 호스트와 컨테이너를 분리해 표로 정리했습니다.** `docker run` 방식은 호스트 8081 → 컨테이너 80, Compose 방식은 `.env` 의 `HOST_PORT` / `NGINX_PORT` 가 결정합니다. 분리해 둔 이유는 호스트 포트가 점유됐을 때 **컨테이너 쪽은 그대로 두고 호스트 포트만 바꾸면 되기 때문**입니다. 실제로 15-2에서 그렇게 해결했습니다.
>
> **볼륨은 이름 있는 볼륨을 썼습니다.** 호스트 경로에 의존하지 않아 다른 머신에서도 같은 명령이 동작하고, 명시적으로 이름을 줘야 `docker volume ls` 로 추적·백업이 가능하기 때문입니다. 익명 볼륨은 나중에 어떤 볼륨이 무엇인지 알 수 없습니다.
>
> 그리고 **클론부터 정리까지 복사-실행 가능한 명령 시퀀스를 한 블록으로 제공**했습니다. `.env` 가 커밋되지 않으므로 `cp .env.example .env` 단계를 명시적으로 포함시켰습니다.

**📄 증거 위치**: 보고서 **13번 재현 절차 (포트/볼륨)**

**💻 실연 명령**

```bash
cat .env.example
docker compose config | grep -A4 ports    # .env 치환 결과
```

**꼬리질문 대비**
- *"`.env` 를 커밋하면 더 편하지 않나?"* → 편하지만 위험하다. 실제 값에는 비밀번호나 API 키가 들어가기 쉽고, 한번 커밋하면 이력에 영구히 남아 나중에 지워도 복구 가능하다. 구조는 `.env.example` 로 공유하고 값은 각자 로컬에 둔다.
- *"바인드 마운트는 왜 안 썼나?"* → 호스트 경로에 의존해서 다른 컴퓨터에서 깨진다. 개발 중 소스 실시간 반영이 목적이면 바인드 마운트가 낫지만, 이번엔 재현성이 우선이라 볼륨을 택했다.

## 3-1. 이미지와 컨테이너의 차이를 "빌드/실행/변경" 관점에서 구분해 설명할 수 있는가?

**⚡ 30초 답변**
> **빌드 관점**에서 이미지는 `docker build` 의 산출물이고 읽기 전용 레이어가 쌓인 불변 스냅샷입니다. 컨테이너는 빌드되지 않고 이미지에서 생성될 뿐입니다.
>
> **실행 관점**에서 이미지는 그 자체로 실행되지 않습니다. `docker run` 이 이미지 위에 쓰기 가능 레이어를 얹어 만든 실행 인스턴스가 컨테이너입니다.
>
> **변경 관점**에서 이미지를 바꾸려면 다시 빌드해야 하고 새 ID가 생깁니다. 컨테이너에서 일어난 변경은 쓰기 레이어에만 쌓이고 원본 이미지는 그대로입니다. 그래서 이미지 하나로 컨테이너 여러 개를 띄울 수 있습니다.
>
> 실습에서 `my-web:v1` 하나로 `my-app` 과 `my-app2` 를 동시에 띄운 것이 그 증거이고, 11번 대조 실험에서 컨테이너에 만든 파일이 삭제와 함께 사라진 것이 "변경은 컨테이너 레이어에만 남는다"의 증거입니다.

**📄 증거 위치**: 보고서 **14-1** (3관점 표) + **10번**(1:N) + **11번**(변경 소실)

**보조 설명 — 비유가 필요하면**
> 이미지는 붕어빵 틀, 컨테이너는 붕어빵입니다. 틀 하나로 여러 개를 찍고, 붕어빵을 먹어도 틀은 그대로입니다. 프로그래밍으로 치면 클래스와 인스턴스 관계입니다.

**꼬리질문 대비**
- *"컨테이너 3개를 띄우면 디스크를 3배 쓰나?"* → 아니다. 이미지 레이어는 공유되고 컨테이너마다 얇은 쓰기 레이어만 추가된다. Copy-on-Write 방식이라 수정한 파일만 복사된다.
- *"컨테이너 안에서 `apt install` 한 걸 남기려면?"* → Dockerfile에 `RUN apt install` 로 써서 이미지에 굽거나, 데이터라면 볼륨을 쓴다. 컨테이너 안 변경은 삭제 시 사라진다.

## 3-2. 컨테이너 내부 포트로 직접 접속할 수 없는 이유와 필요한 이유를 설명할 수 있는가?

**⚡ 30초 답변**
> **접속할 수 없는 이유**는 컨테이너가 독립된 네트워크 네임스페이스와 자체 IP를 갖기 때문입니다. 호스트에서 `localhost:80` 을 치면 호스트 자신의 80번을 찾지, 컨테이너의 80번을 찾지 않습니다. 둘은 애초에 다른 네트워크 공간입니다.
>
> **포트 매핑이 필요한 이유는 세 가지**입니다. 첫째 격리 유지 — 모든 포트를 자동 공개하면 격리의 의미가 없으니 공개할 포트를 명시적으로 고르게 합니다. 둘째 포트 충돌 회피 — 컨테이너가 전부 내부 80번을 써도 호스트 포트만 다르면 공존합니다. 셋째 이식성 — 내부 포트는 이미지에 고정하고 호스트 포트만 환경에 맞춰 바꿀 수 있습니다.
>
> 그리고 중요한 점은 **포트 매핑이 호스트 경계를 넘을 때만 필요하다**는 겁니다. 17-2에서 `client` 컨테이너는 포트 매핑이 전혀 없는데도 `http://web:8080` 으로 접속에 성공했습니다.

**📄 증거 위치**: 보고서 **14-2** + **17-2** (컨테이너 간 통신)

**결정적 증거 — 로그의 출처 IP**

```
172.18.0.3 - - [...] "GET / HTTP/1.1" 200 23 "-" "curl/8.21.0"   ← client 컨테이너 (직통)
172.18.0.1 - - [...] "GET / HTTP/1.1" 200 23 "-" "curl/8.7.1"    ← 호스트 (게이트웨이 경유)
```

> 같은 요청인데 출처가 갈립니다. 컨테이너끼리는 `172.18.0.x` 대역에서 직접 통신하고, 호스트에서 온 요청만 게이트웨이를 통과합니다.

**💻 실연 명령**

```bash
docker compose up -d && sleep 8
docker compose logs client      # <h1>hello, world!</h1> — 포트 매핑 없이 통신
docker compose logs --tail 3 web  # 출처 IP 확인
docker compose down
```

**꼬리질문 대비**
- *"그럼 DB 컨테이너는 포트를 안 열어도 되나?"* → 그렇다. 앱 컨테이너가 같은 네트워크에서 서비스명으로 접속하면 된다. 포트를 안 열수록 공격 표면이 줄어든다.

## 3-3. 절대 경로/상대 경로를 어떤 상황에서 선택하는지 설명할 수 있는가?

**⚡ 30초 답변**
> 판단 기준은 한 줄로 정리됩니다. **실행 위치가 달라져도 같은 대상을 가리켜야 하면 절대 경로, 프로젝트를 통째로 옮겨도 따라와야 하면 상대 경로**입니다.
>
> 실습에서 적용한 예를 들면, Dockerfile의 `COPY index.html` 은 **상대 경로**입니다. 빌드 컨텍스트 기준으로 해석되므로 저장소를 어디에 클론하든 동작해야 하기 때문입니다. 여기에 절대 경로를 쓰면 제 컴퓨터에서만 빌드됩니다.
>
> 반대로 볼륨 마운트의 `-v my-vol:/data` 에서 `/data` 는 **절대 경로**여야 합니다. 컨테이너 내부 경로는 규칙상 `/` 로 시작해야 합니다.
>
> 스크립트나 cron처럼 **실행 시점의 작업 디렉토리를 예측할 수 없는 경우**에도 절대 경로를 씁니다. 상대 경로를 쓰면 어디서 실행되느냐에 따라 결과가 달라집니다.

**📄 증거 위치**: 보고서 **14-3** (상황별 선택 표)

**정리 표** (외우기보다 기준을 이해할 것)

| 상황 | 선택 | 이유 |
| :--- | :--- | :--- |
| `COPY index.html ...` | 상대 | 클론 위치와 무관해야 함 |
| `docker build .` | 상대 | 현재 위치 기준 |
| `-v my-vol:/data` | 절대 | 컨테이너 내부 경로 규칙 |
| cron·스크립트의 파일 참조 | 절대 | 작업 디렉토리 예측 불가 |

**꼬리질문 대비**
- *"`./` 와 `../` 는?"* → `.` 은 현재 디렉토리, `..` 은 상위. `cd ../..` 처럼 두 단계 위로도 갈 수 있다.
- *"`~` 는 절대 경로인가?"* → 셸이 홈 디렉토리 절대 경로로 확장해 준다. 다만 셸이 확장하는 것이라 일부 설정 파일이나 프로그램에서는 그대로 문자로 취급돼 동작하지 않을 수 있다.

## 3-4. 파일 권한 숫자 표기(예: 755, 644)가 어떤 규칙으로 결정되는지 설명할 수 있는가?

**⚡ 30초 답변**
> **1단계, 각 권한에 값이 있습니다.** 읽기 `r` 은 4, 쓰기 `w` 는 2, 실행 `x` 는 1입니다.
>
> **2단계, 대상별로 합산해 세 자리를 만듭니다.** 순서는 소유자·그룹·기타입니다.
>
> 예를 들어 755는 소유자가 4+2+1=7로 `rwx`, 그룹이 4+0+1=5로 `r-x`, 기타가 5로 `r-x` 가 되어 `rwxr-xr-x` 입니다. 644는 `rw-r--r--` 이고요.
>
> 실습에서 쓴 값으로 보면, `note.txt` 에 준 600은 `rw-------` 로 소유자만 읽고 쓸 수 있고, `workspace` 에 준 700은 `rwx------` 입니다.
>
> **주의할 점이 하나 있는데, 디렉토리에서 `x` 는 "실행"이 아니라 "진입" 권한**입니다. 디렉토리에 `r` 만 있고 `x` 가 없으면 이름 목록은 볼 수 있어도 안으로 들어가거나 내부 파일 정보를 읽을 수 없습니다. 그래서 디렉토리는 보통 755나 700처럼 `x` 를 포함해 줍니다.

**📄 증거 위치**: 보고서 **14-4** (계산 표 + 디렉토리 x 설명)

**칠판에 그려도 되는 계산 예**

```
755  →  rwx  r-x  r-x
        7    5    5
      4+2+1 4+0+1 4+0+1
      소유자  그룹  기타
```

**실전 연결 — 이 답변을 강하게 만드는 한마디**
> 이 규칙이 실제로 강제되는 사례가 SSH입니다. 개인키 파일 권한이 `600` 이 아니면 SSH가 경고를 내고 **키 사용을 아예 거부**합니다. 보고서 17-5에 `ls -l` 로 실측한 출력이 있는데 개인키는 `-rw-------`(600), 공개키는 `-rw-r--r--`(644)로 갈립니다. 공개키는 어차피 배포하는 값이라 열어둬도 되고, 개인키는 남이 읽으면 계정을 탈취당하기 때문입니다.

**꼬리질문 대비**
- *"777은?"* → 모두가 읽고 쓰고 실행할 수 있다. 문제를 "해결"하려고 쓰는 경우가 많은데 보안상 거의 항상 잘못된 선택이다.
- *"`chmod u+x` 같은 표기는?"* → 기호 표기다. `u`(소유자) `g`(그룹) `o`(기타) `a`(전체)에 `+`/`-`/`=` 로 권한을 조정한다. 기존 권한을 유지하며 일부만 바꿀 때 편하다.

## 4-1. "호스트 포트가 이미 사용 중"이라 포트 매핑이 실패한다면, 어떤 순서로 원인을 진단할지 설명할 수 있는가?

**⚡ 답변 — 5단계로 말한다**

> **1단계, 에러 메시지부터 끝까지 읽습니다.** 실제로 겪은 메시지는 이랬습니다.
>
> ```
> Bind for 0.0.0.0:8081 failed: port is already allocated.
> ```
>
> 여기서 이미 두 가지를 알 수 있습니다. 문제는 컨테이너 내부가 아니라 **호스트 포트 8081** 이고, 원인은 권한이나 설정이 아니라 **이미 점유됨**입니다.
>
> **2단계, 누가 점유 중인지 확인합니다.**
>
> ```bash
> lsof -i :8081
> ```
>
> **3단계, 그게 Docker 컨테이너인지 확인합니다.** `docker ps` 로 8081을 쓰는 컨테이너를 특정합니다. Docker가 아닌 다른 프로그램일 수도 있어서 이 구분이 필요합니다.
>
> **4단계, 선택합니다.** 기존 컨테이너가 필요하면 새 컨테이너의 **호스트 포트**를 바꾸고, 필요 없으면 정리합니다. 핵심은 **고칠 대상이 이미지나 컨테이너 포트가 아니라 호스트 포트 하나**라는 점입니다.
>
> **5단계, `curl` 로 재검증합니다.**
>
> 실제로 저는 컨테이너 포트 80은 그대로 두고 호스트 포트만 8082로 바꿔서, 두 컨테이너가 8081과 8082로 공존하게 만들었습니다.

**📄 증거 위치**: 보고서 **15-2** (실제 재현 + 해결)

**놓치기 쉬운 점 — 이걸 말하면 가산점**
> 한 가지 더 있는데, **`docker run` 이 실패해도 컨테이너는 생성됩니다.** 에러 메시지 위에 컨테이너 ID가 찍히는 게 그 증거입니다. 그래서 재시도 전에 `docker rm` 을 하지 않으면 "이름이 이미 사용 중"이라는 두 번째 에러를 만납니다.

## 4-2. 컨테이너 삭제 후 데이터가 사라진 경험이 있다면, 이를 방지하기 위한 대안을 설명할 수 있는가?

**⚡ 답변 — 경험 → 원인 → 대안 순으로**

> **경험이 있습니다.** 11번 실습에서 컨테이너 안 `/tmp` 에 파일을 만들고 컨테이너를 지웠더니 `No such file or directory` 가 나왔습니다.
>
> **원인은 저장 위치입니다.** 컨테이너는 이미지 위에 쓰기 레이어를 얹은 구조인데, 이 레이어의 수명이 컨테이너와 같습니다. `/tmp` 에 쓴 건 쓰기 레이어에 쌓였고 `docker rm` 과 함께 사라진 겁니다.
>
> **중요한 건, 원인이 "컨테이너 삭제"라는 행위가 아니라는 점입니다.** 그걸 확인하려고 대조 실험을 했습니다. 같은 이미지, 같은 명령인데 저장 위치만 볼륨으로 바꿨더니 컨테이너를 지워도 데이터가 남았습니다. 즉 결정하는 건 **어디에 썼는가**입니다.
>
> **대안은 세 가지를 비교했습니다.**
>
> | 대안 | 방식 | 적합한 상황 | 유의점 |
> | :--- | :--- | :--- | :--- |
> | 이름 있는 볼륨 | `-v my-vol:/data` | DB 등 운영 데이터 (채택) | 호스트 경로 비의존, 이식성 좋음 |
> | 바인드 마운트 | `-v $(pwd)/data:/data` | 개발 중 소스 실시간 반영 | 호스트 경로 의존, 다른 머신에서 깨짐 |
> | 정기 백업 | `tar` 로 볼륨 아카이브 | 볼륨 자체의 유실 대비 | 볼륨도 `volume rm` 하면 끝 |
>
> 이번엔 재현성이 중요해서 이름 있는 볼륨을 택했습니다.

**📄 증거 위치**: 보고서 **11번**(대조 실험) + **15-3**(대안 비교표)

**마무리 한마디 — 실무 감각을 보여주는 부분**
> 그리고 운영에서 특히 조심할 게 하나 있는데, **`docker compose down` 은 볼륨을 남기지만 `down -v` 는 볼륨까지 지웁니다.** 정리한다고 습관적으로 `-v` 를 붙이면 데이터가 통째로 날아갑니다. 그래서 보고서 17-3에 경고로 적어 뒀습니다.

## 4-3. 이 미션에서 가장 어려웠던 지점과, 해결 과정(가설 → 확인 → 조치)을 근거와 함께 설명할 수 있는가?

**⚡ 답변 — 하나를 골라 4단계로 말한다**

> **가장 어려웠던 건 환경 변수 치환의 동작 범위를 잘못 예상한 것**이었습니다.
>
> **현상**: 보너스 4에서 nginx 템플릿에 포트를 환경 변수로 넣고, 옆에 설명 주석을 달았습니다. 그런데 컨테이너 안의 결과 파일에서 주석 문장이 깨져 있었습니다. `# ${NGINX_PORT} 는 ... 치환된다` 라고 쓴 게 `# 8080 는 ... 치환된다` 가 되어 문장이 성립하지 않았습니다.
>
> **가설**: 처음엔 "설정 파일의 주석은 파서가 무시하니까 치환 대상도 아닐 것"이라고 생각했습니다. 그래서 다른 원인을 찾으려 했습니다.
>
> **확인**: 템플릿 원본만 봐서는 문제가 안 보였습니다. 그래서 컨테이너 안의 **결과물**을 직접 열었습니다.
>
> ```bash
> docker compose exec web cat /etc/nginx/conf.d/default.conf
> ```
>
> 열어 보니 주석까지 치환돼 있었습니다. 제 가설이 틀린 겁니다.
>
> **조치**: 주석에서 변수 표기를 빼고 "아래 리슨 포트는 ~" 처럼 서술형으로 바꿨습니다.
>
> **근거와 교훈**: 원인은 envsubst가 nginx 설정 문법을 이해하는 도구가 아니라 **단순 텍스트 치환기**라는 점이었습니다. `${...}` 패턴이 보이면 주석이든 아니든 무조건 바꿉니다. "설정 파일이니 파서가 알아서 하겠지"라는 추측이 틀렸던 거죠.
>
> 여기서 배운 건 **템플릿을 다룰 때는 입력이 아니라 출력을 검증해야 한다**는 것입니다. 원본만 보면 안 보이는 문제가 있습니다.

**📄 증거 위치**: 보고서 **16번 미션 회고** + **15-4**

**두 번째 사례도 준비해 두기** (하나 더 물으면)

> 볼륨 대조 실험을 짤 때 `docker exec` 가 붙지 않았습니다. `container ... is not running` 이었는데, 가설은 "컨테이너가 이미 종료돼서 exec가 붙을 프로세스가 없다"였고, `docker ps -a` 에서 `Exited (0)` 을 확인했습니다. `sh -c "echo ..."` 는 즉시 끝나는 명령이라 컨테이너도 곧바로 종료된 겁니다. `sleep 300` 으로 살려 둔 뒤 실험을 재설계해서 해결했고, **컨테이너의 수명은 PID 1 프로세스의 수명과 같다**는 걸 실감했습니다. 컨테이너는 켜 두는 상자가 아니라 프로세스를 감싼 것이더군요.

**이 항목에서 감점되지 않는 법**
- ❌ "다 잘 됐습니다" → 어려움이 없었다는 건 깊이 안 해봤다는 신호로 읽힌다
- ❌ "구글에서 찾아서 고쳤습니다" → 사고 과정이 없다
- ✅ **틀린 가설을 그대로 말한다** → 가설을 세우고 검증해서 기각했다는 게 핵심이다

## 5-1. Docker Compose 기초

> `docker-compose.yml` 에 단일 `web` 서비스를 정의하고 `build: .` 로 기존 Dockerfile을 재사용했습니다. 보고서 17-1에 **10번의 `docker run` 명령과 Compose 정의를 1:1 대응표**로 나란히 놓았습니다.
>
> 배움 포인트는 "왜 문서화된 실행 설정인가"인데, 10번에서는 `docker run -d -p 8081:80 --name my-app my-web:v1` 이라는 명령을 사람이 기억하고 매번 정확히 쳐야 했습니다. 인자를 하나라도 빠뜨리면 다르게 동작하는데 그게 어디에도 기록되지 않습니다. Compose로 옮기면 파일로 남아서 저장소에 커밋되고, 코드 리뷰 대상이 되고, `git diff` 로 변경이 드러납니다. **실행 방법이 개인의 기억에서 저장소의 자산으로 바뀌는 것**이 핵심입니다.

## 5-2. Docker Compose 멀티 컨테이너

> `web` 에 더해 `client` 서비스를 추가해 2개를 함께 실행했습니다. `client` 는 `curl -s http://web:8080/` 을 실행하고, `docker compose logs client` 에 `<h1>hello, world!</h1>` 가 찍힙니다.
>
> 이 한 줄이 세 가지를 동시에 증명합니다. 컨테이너 간 통신이 되고, 서비스명 `web` 이 DNS로 해석되고, 빌드한 이미지가 실제로 `index.html` 을 서빙한다는 것입니다.
>
> 서비스 디스커버리는 Compose가 프로젝트 전용 네트워크를 만들고 그 안에 서비스명을 DNS로 등록해 주기 때문에 동작합니다. 컨테이너 IP는 재시작마다 바뀌어서 하드코딩하면 깨지지만 서비스명은 안정적입니다.

## 5-3. Compose 운영 명령어

> `up` / `ps` / `logs` / `down` 을 각각 실행해 출력을 기록했습니다. 상태 확인 루틴으로 정리하면 **`ps -a` 로 무엇이 죽었는지 → `logs` 로 왜 죽었는지 → `up -d` 로 재기동** 순입니다.
>
> 두 가지 함정을 기록했는데, 첫째는 `ps` 가 실행 중인 것만 보여줘서 `client` 처럼 끝나는 서비스는 `-a` 를 써야 보인다는 점, 둘째는 `down` 과 `down -v` 의 차이입니다.

## 5-4. 환경 변수 활용

> nginx 공식 이미지의 envsubst 템플릿 기능을 썼습니다. `.env` 의 `NGINX_PORT` 만 8080에서 8090으로 바꾸고 **`--build` 없이** 재기동했더니 컨테이너 내부 리슨 포트가 바뀌었습니다. 이미지 생성 시각이 그대로인 것으로 재빌드가 없었음을 확인했습니다.
>
> 여기서 중요한 건 **내부 구성은 바뀌었는데 사용자가 접속하는 주소(`localhost:8081`)는 그대로**라는 점입니다. 설정과 코드를 분리하면 이미지 하나로 개발·스테이징·운영을 다 커버할 수 있고, 테스트한 그 이미지가 그대로 운영에 올라갑니다.
>
> 실제 값이 담긴 `.env` 는 `.gitignore` 로 제외하고 `.env.example` 만 커밋했습니다. 구조는 공유하되 값은 각자 두는 방식입니다.

## 5-5. GitHub SSH 키 설정

> `ed25519` 로 키를 생성해 GitHub에 등록하고, `ssh -T git@github.com` 으로 `successfully authenticated` 를 확인한 뒤 원격을 HTTPS에서 SSH로 전환했습니다. 실제로 이 저장소는 SSH로 푸시했습니다.
>
> 인증 방식 차이는, HTTPS가 토큰을 매 요청마다 서버에 제시하는 반면 SSH는 키 쌍 기반이라 **개인키가 로컬을 벗어나지 않습니다.** 서버가 보낸 챌린지에 개인키로 서명해 응답하고 서버는 등록된 공개키로 검증합니다.
>
> 등록 과정에서 `Key is invalid` 오류를 겪었는데, 원인은 공개키 원문 대신 **지문**을 붙여넣은 것이었습니다. 15-5에 진단 과정을 기록했습니다.
>
> 보안 습관 관련해서 하나 덧붙이면, **이 키에는 passphrase를 걸지 않았습니다.** 개인 노트북의 학습용 저장소라 편의를 택했는데, 위험이 없다는 뜻이 아니라 알고 감수한 선택입니다. 파일 권한 600으로 보완하고 있고, 공용 PC나 운영 서버 접근 키라면 반드시 걸어야 한다고 17-5에 명시했습니다.

**💻 보너스 통합 실연**

```bash
cd ~/Desktop/codyssey/workspace-decoration
docker compose up -d && sleep 8
docker compose ps -a                    # 5-2, 5-3
docker compose logs client              # 5-2 핵심 증거
docker compose exec web env | grep -E "NGINX_PORT|APP_MODE"   # 5-4
curl -s localhost:8081
docker compose down                     # 5-3
ssh -T git@github.com                   # 5-5 (exit 1이 정상)
git remote -v                           # SSH URL 확인
```

## 자주 나올 만한 마무리 질문

**"이 프로젝트에서 가장 배운 점은?"**
> 기능을 돌리는 것보다 **왜 그렇게 동작하는지 확인하는 절차**를 만드는 게 어려웠습니다. 특히 볼륨 실습에서 "되는 경우"와 "안 되는 경우"를 나란히 실행하는 대조 실험을 해 보니, 데이터 소실의 원인이 컨테이너 삭제가 아니라 저장 위치라는 게 한눈에 보였습니다. 앞으로도 결과만 기록하지 않고 대조군을 함께 남기려고 합니다.

**"더 개선한다면?"**
> 세 가지를 생각하고 있습니다. 첫째, `depends_on` 이 시작 순서만 보장하고 준비 완료는 보장하지 않아서 지금은 `sleep 3` 으로 우회했는데, healthcheck와 `condition: service_healthy` 로 바꾸는 게 맞습니다. 둘째, `nginx:latest` 를 쓰고 있는데 운영이라면 `nginx:1.27` 처럼 버전을 고정해야 합니다. 셋째, SSH 키에 passphrase를 걸지 않았는데 접근 범위가 넓어지면 반드시 추가해야 합니다.
